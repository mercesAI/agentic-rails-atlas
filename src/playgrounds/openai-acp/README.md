# OpenAI ACP playground

Client-side simulation of the Agentic Commerce Protocol (OpenAI and Stripe), following the spec folders `2025-09-29` and `2026-04-17` in `research/vendor/acp/spec`. Field names, enums and headers come from the JSON Schema and OpenAPI files, not from RFC examples. A version toggle switches between the two. Every payload is labeled "Illustrative example, spec version X". No network calls, no real merchants, funds or cards. Card data is a fixture string (`card_number_type: network_token`), never a card number.

## What it covers

1. **Checkout session state machine** (`lib/checkout.ts`, `lib/server.ts`). Create (201), update, get, complete and cancel against a fixture merchant with a request and response log. 2025-09-29 has five statuses; 2026-04-17 has eleven and adds `incomplete`, `requires_escalation`, `authentication_required`, `pending_approval`, `complete_in_progress` and `expired`. The transition table mirrors `src/content/states/openai-acp-checkout-session.json`; every edge is labeled stated, implied or inferred, and a test compares the table with that file. Spec-defined outcomes keep their codes: 405 on cancel of a finished session, `requires_3ds` with `param: $.authentication_result` when `authentication_result` is missing, and the idempotency errors.
2. **Delegate Payment allowance** (`lib/delegate.ts`). `POST /agentic_commerce/delegate_payment` with `payment_method`, `allowance` (`reason`, `max_amount`, `currency`, `checkout_session_id`, `merchant_id`, `expires_at`), `risk_signals` and `metadata`, validated against the required lists in the schema (400 for a missing field, 422 for a semantic error, code `invalid_card`). The token is then presented at complete. Failure injection: exceed `max_amount`, let `expires_at` pass (simulated clock), wrong `merchant_id`, wrong `checkout_session_id`, wrong currency, reuse of a `one_time` token. The spec says the token must only work within the allowance and must become invalid at or after `expires_at`, but names no error code and no status for a break. The UI says so on every refusal.
3. **Order webhook signature** (`lib/webhook.ts`). `Merchant-Signature: t=<unix_seconds>,v1=<64_hex>`, HMAC-SHA256 over `t + "." + raw_body` with WebCrypto and an ephemeral in-memory secret, for `order_create` and `order_update` events. Failure injection: tampered body, wrong secret, missing header, malformed header, and a receiver clock more than 300 seconds from `t`. The receiver answers 401 with `type: invalid_request`, `code: invalid_signature` and the messages from the OpenAPI examples.
4. **Idempotency** (`lib/idempotency.ts`). Same key and body replays the stored response with `Idempotent-Replayed: true`; same key and a different body gives 422 `idempotency_conflict`; a duplicate while the first request runs gives 409 `idempotency_in_flight` with `Retry-After`; a missing key gives 400 `idempotency_key_required`; keys expire after 24 hours; 5xx is not cached. Equality is semantic JSON equality of the body.
5. **Discovery and payment handlers** (`lib/handlers.ts`, 2026-04-17 only). The `/.well-known/acp.json` document (`DiscoveryResponse`: `protocol`, `api_base_url`, `transports`, `capabilities`) is editable and checked for required keys. Session `capabilities.payment.handlers` objects carry the required `PaymentHandler` keys; the agent picks which handler names it supports and the table shows which seller handlers are usable. In 2025-09-29 the tab explains that neither exists (`payment_provider` and `payment_data.provider: stripe` instead).

## Teaching simplifications (labeled in the UI)

- Handler matching compares the reverse-DNS `name` only; the spec states no matching algorithm. Handler names other than `dev.acp.*`, PSP values, URLs and all identifiers are fixtures.
- In 2026-04-17 `CheckoutSessionCreateRequest.line_items` holds `Item` objects, and the schema `Item` has no `quantity`. The fixture merchant uses quantity 1 there; 2025-09-29 sends `items[].quantity`.
- An allowance break answers the complete call with HTTP 200, the unchanged session and a `payment_declined` message (an existing `MessageError` code). The spec names no code or status for this case.
- A call that does not fit the current status (update after cancel, complete before ready) returns `4XX` with the fixture code `invalid_state`; unknown sessions return 404 with the fixture code `not_found`; the spec gives no body for these.
- Idempotency behavior follows the 2026-04-17 RFC in both versions; the 2025-09-29 files make the header optional and define no replay header or errors. The in-flight case is staged with a button, not with real concurrency.
- The webhook scheme shown is the 2026-04-17 one in both versions. The 2025-09-29 file only says "HMAC signature over the raw request body".
- Merchant-side moves (`authentication_required`, `requires_escalation`, settling `complete_in_progress` or `in_progress`) are buttons; the spec states no trigger for them. 3DS content (`authentication_metadata`) is a shaped fixture, and `authentication_result.outcome` other than `authenticated` or `attempt_acknowledged` is refused with `payment_declined`.
- Tax is a flat 8 percent, shipping a single fixture option. Totals use integer minor units.

## Tests

`tests/unit/playgrounds/openai-acp.test.ts` covers every exported function. It checks request and response payloads against the vendored JSON Schemas with a small walker (required keys, unknown keys under `additionalProperties: false`, enums), compares the transition table with the state file, and cross-checks OpenAPI paths. Vendor-dependent checks are skipped when `research/vendor/acp` is absent.
