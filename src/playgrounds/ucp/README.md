# UCP playground

Client-side simulation of the Universal Commerce Protocol, following the spec at tag **v2026-08-25** (`research/vendor/ucp`, checked with `git show v2026-08-25:...`; `main` is ahead and counts as draft). Every payload is labeled "Illustrative example, spec version v2026-08-25". No network calls, no real stores, handlers or keys.

## What it covers

1. **Profile negotiation** (`lib/negotiate.ts`). Two editable JSON profiles: the business profile at `/.well-known/ucp` (`ucp { version, services, capabilities, payment_handlers, supported_versions }` plus top-level `keys[]`) and the agent profile named in `UCP-Agent: profile="..."`. The simulator shape-checks both (`profile_malformed`, including private JWK members in `keys[]` and `supported_versions` in a leaf or platform profile), validates the agent version against `version` and `supported_versions` (leaf profile for 2026-04-08, `version_unsupported` 422 / MCP -32001 otherwise), rejects entries that fail authority binding or `dev.ucp.*` entries not on the selected release date, intersects capabilities, picks the highest common version, prunes orphaned extensions round by round, and flags `capabilities_incompatible` when nothing is left. Each prune has a reason. Nine scenarios load preset edits.
2. **Payment handlers** (`lib/payment.ts`). The business filters handlers by cart context (installments are removed for subscription items), resolves `available_instruments` against the agent declaration (brand enums intersect), and checks the Complete Checkout submission: exactly one instrument unless `dev.ucp.common.payment.split_payments` is active, each from an offered handler within its constraints, else `payment_failed`. Credentials are never echoed back.
3. **Checkout state machine** (`lib/checkout.ts`). `incomplete`, `requires_escalation` (with `continue_url` and a `requires_buyer_input` or `requires_buyer_review` message), `ready_for_complete`, `complete_in_progress`, `completed`, `canceled` (cancel from any non-terminal state, or expiry after the default 6 hour TTL). Update is a full replacement and is refused during `complete_in_progress`; Complete only from `ready_for_complete`; `mandate_required` when AP2 is negotiated (security lock) and no `ap2.checkout_mandate` is sent. Failure injection: missing `continue_url` on escalation (flagged as a spec violation), idempotency key reused with a changed body (409), second instrument without split payments, disallowed card brand, expiry, calls in the wrong state.
4. **Transport switcher** (`lib/transport.ts`). The same operation as REST (`POST /checkout-sessions`, `GET` and `PUT /checkout-sessions/{id}`, `POST .../complete`, `POST .../cancel` under the service endpoint, with `UCP-Agent`, `Request-Id`, `Idempotency-Key`), MCP (`tools/call` with `create_checkout`, `get_checkout`, `update_checkout`, `complete_checkout`, `cancel_checkout`, `meta["ucp-agent"]`, `meta["idempotency-key"]` on complete and cancel, top-level `id`, `result.structuredContent`) and A2A (`message/send` with `X-A2A-Extensions: https://ucp.dev/2026-08-25/specification/reference`, actions `add_to_checkout` and `complete_checkout`, `DataPart` keys `a2a.ucp.checkout`, `a2a.ucp.checkout.payment`, `a2a.ucp.checkout.signals`).

## Teaching simplifications (labeled in the UI)

- A payment handler counts as usable only when the agent profile also declares it; constraints merge only for `properties.<name>.enum`.
- Handler names (`com.example.*`), configs, credential types and tokens are fixtures. The business is `juniper.example`, the agent `agent.example`.
- The business rules (buyer email, delivery window, review threshold, 8 percent tax) are fixtures; fulfillment, discounts and Actions (3DS2) are not modeled.
- `update_not_allowed` is a fixture code: the spec requires a recoverable error during `complete_in_progress` but names no code. Calls the spec answers with an unnamed error (complete outside `ready_for_complete`, cancel of a terminal session) are shown as notes, not wire codes. `payment_failed` and `mandate_required` use severity `recoverable` and keep the status unchanged.
- A2A get, update and cancel use natural-language text parts, since the binding gives structured actions only for adding items and completing. Parts use `kind` (the spec examples mix `type` and `kind`). A2A task handling, MCP session setup, authentication and RFC 9421 signature headers are left out.
- `ap2.merchant_authorization` (detached JWS `header..signature`) and `ap2.checkout_mandate` (SD-JWT with `~` separators) are shaped fixtures; nothing is signed. Extension `requires` constraints from extension schemas are not evaluated.
- The leaf profile for 2026-04-08 is a fixture without `keys`; it uses the old AP2 name `dev.ucp.shopping.ap2_mandate`.
