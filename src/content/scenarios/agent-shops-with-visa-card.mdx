## The situation

A consumer asks an AI agent to buy one item from a merchant's own website and pay with a Visa card already linked to the agent. The agent browses like a person would, but it signs every request so that the merchant's CDN can tell it apart from an unknown bot. The consumer is present at one moment only: to approve the purchase with a passkey.

Two Visa layers work together here. The Trusted Agent Protocol (TAP) lets the agent prove its identity by signing its web requests, and it does not move money by itself.<Cite ids="clm-visa-tap-001 clm-visa-tap-002" /> Visa's TAP overview page presented TAP as an enhancement to Visa Intelligent Commerce (VIC), which holds the consumer's consent, the limits and the agent-specific token.<Cite ids="clm-visa-tap-007 clm-visa-tap-129" />

Parts of this run live today. Visa says live European agent purchases used TAP and the Agent Directory, at merchant websites rather than test storefronts.<Cite ids="clm-visa-tap-159 clm-visa-tap-181" /> Cloudflare and Akamai support TAP at the infrastructure level.<Cite ids="clm-visa-tap-152" /> No count of merchants that verify TAP signatures is published, and the specification page has no version number or date.<Cite ids="clm-visa-tap-133 clm-visa-tap-023" />

## Actors

- **Consumer**, who authenticates the Payment Instruction with a passkey.
- **AI agent**, an Agent Provider: a certified AI platform onboarded to the payment scheme.<Cite ids="clm-visa-tap-031" />
- **Visa Intelligent Commerce**, which enrolls the card, holds instructions and returns credentials.
- **Visa key store**, where verifiers get agent public keys.<Cite ids="clm-visa-tap-030" /> The specification named a JWK Set at `mcp.visa.com` as its location until October 2026 and names no URL today.<Cite ids="clm-visa-tap-069" />
- **CDN**, a Site Protection Provider in front of the merchant site.<Cite ids="clm-visa-tap-033" />
- **Merchant**, which may verify signatures itself or let the CDN do it.<Cite ids="clm-visa-tap-035" />
- **Acquirer, network and issuer**, on ordinary card rails.

## Step by step

1. **Ask (no protocol).** The consumer names the item and the merchant.
2. **Enroll the card (VIC).** The agent enrolls the card with `POST /vacp/v1/cards`, as Visa's VIC API client names the call.<Cite ids="clm-visa-tap-143" /> VIC provisions an agent-specific token through the Visa Token Service, then runs issuer step-up where required and passkey setup.<Cite ids="clm-visa-tap-140" />
3. **Browse with a signature (TAP).** The agent sends RFC 9421 `Signature-Input` and `Signature` headers.<Cite ids="clm-visa-tap-037" /> The signature covers at least `@authority` and `@path` and carries `created`, `expires`, `keyid`, `alg`, `nonce` and `tag`.<Cite ids="clm-visa-tap-038 clm-visa-tap-039" /> For browsing the tag is `agent-browser-auth`.<Cite ids="clm-visa-tap-040" />
4. **Fetch the key (TAP).** The CDN resolves `keyid` against Visa's key store. On 2026-10-11 and 2026-10-19 the JWK Set the specification used to name held one 2048-bit RSA key and no Ed25519 key.<Cite ids="clm-visa-tap-071" /> The key carried a certificate for `vic-oauth-jwe.visa.com` from a Visa sandbox issuing CA.<Cite ids="clm-visa-tap-072" /> Visa's own code uses it to encrypt tokens for Visa's MCP server.<Cite ids="clm-visa-tap-239" /> Visa has not published how production agent keys are distributed.<Cite ids="clm-visa-tap-074" />
5. **Verify at the edge (TAP).** The CDN checks, in order, the tag, the minimum fields, the time window, the nonce, the key and the signature.<Cite ids="clm-visa-tap-075" /> The window is at most 8 minutes.<Cite ids="clm-visa-tap-043" />
6. **Forward (TAP).** The CDN passes the request on as a verified agent.<Cite ids="clm-visa-tap-085" />
7. **Product page (TAP).** The merchant returns product details, availability and the final cost after taxes and shipping.<Cite ids="clm-visa-tap-237" /> It may show a simpler agent-specific page.<Cite ids="clm-visa-tap-234" />
8. **Authenticate with a passkey (VIC).** The consumer authenticates the purchase instruction with a Visa Payment Passkey or another issuer-approved method; without it the agent cannot retrieve credentials.<Cite ids="clm-visa-tap-141" />
9. **Create the Payment Instruction (VIC).** The agent calls `POST /vacp/v1/instructions`, and Visa's client sends the authentication result inside that request.<Cite ids="clm-visa-tap-142 clm-visa-tap-245" />
10. **Get credentials (VIC).** The agent calls `POST /vacp/v1/instructions/{instructionId}/credentials`.<Cite ids="clm-visa-tap-142" />
11. **Check out with the payer tag (TAP).** The agent signs with `agent-payer-auth`.<Cite ids="clm-visa-tap-040" /> For a key-entered guest checkout, the payment path Visa's VIC page named first, the agent fills the merchant's card form.<Cite ids="clm-visa-tap-144" /> The body carries `agenticConsumer` (`nonce`, `idToken`, `contextualData`, `kid`, `alg`, `signature`) and `agenticPaymentContainer` (`nonce`, `kid`, `alg`, `signature`).<Cite ids="clm-visa-tap-047 clm-visa-tap-056" /> For key-entered guest checkout the container carries a payment credential hash.<Cite ids="clm-visa-tap-059" /> Both objects use the header's key and nonce.<Cite ids="clm-visa-tap-078" />
12. **Verify the payer signature (TAP).** The CDN repeats the header checks for the payer tag.<Cite ids="clm-visa-tap-075" />
13. **Verify the body (TAP).** The merchant verifies each object over all fields in the order received except the signature.<Cite ids="clm-visa-tap-079" /> If its own hash of the key-entered card data does not match, it should decline.<Cite ids="clm-visa-tap-060" />
14. **Authorize (card rails).** The merchant authorizes through its acquirer; TAP plays no part in this step.<Cite ids="clm-visa-tap-002" />
15. **Confirm (no protocol).** The merchant returns the order result; TAP defines no receipt.<Cite ids="clm-visa-tap-130" />
16. **Report (VIC).** The agent calls `POST /vacp/v1/instructions/{instructionId}/confirmations`.<Cite ids="clm-visa-tap-142" />

## Which protocol does what

| Steps | Protocol | Object or message | Spec version |
|---|---|---|---|
| 2, 8 to 10, 16 | VIC (Visa) | `/vacp/v1/cards`, `/vacp/v1/instructions` and its sub-paths | visa/ai client, 2026-09-30 |
| 3 to 7 | TAP | `Signature-Input` with `tag="agent-browser-auth"`, JWK Set | unversioned page, read 2026-10-11, rechecked 2026-10-19 |
| 11 to 13 | TAP | `tag="agent-payer-auth"`, `agenticConsumer`, `agenticPaymentContainer` | unversioned page, read 2026-10-11, rechecked 2026-10-19 |
| 14 | Card rails | authorization | outside TAP |

Two warnings for implementers. The specification's header examples reuse a Web Bot Auth draft test vector that signs a different base.<Cite ids="clm-visa-tap-114" /> Its browsing and checkout examples show the same signature under different tags, and its example window is 3,600 seconds, so the examples cannot verify.<Cite ids="clm-visa-tap-116 clm-visa-tap-115" /> TAP publishes no test vectors.<Cite ids="clm-visa-tap-064" />

## Where controls apply

- **Before authorization.** VIC holds consent: the consumer authenticates each Payment Instruction with a Visa Payment Passkey or another issuer-approved method.<Cite ids="clm-visa-tap-141" /> Spending limits and step-up also sit in VIC, invisible to the merchant in the TAP request.<Cite ids="clm-visa-tap-129" />
- **At signing.** TAP allows extra signature fields beyond the minimum.<Cite ids="clm-visa-tap-046" /> The minimum leaves out `@method`, the query string and a content digest, so an agent platform that adds them narrows what a stolen signature could be reused for.<Cite ids="clm-visa-tap-117" />
- **At the edge.** The CDN is the natural verifier.<Cite ids="clm-visa-tap-035" /> Nonce checks work only if the verifier keeps an 8-minute record.<Cite ids="clm-visa-tap-077" /> The sample CDN proxy checks only `/product/` paths, logs the tag without checking it and enforces no 8-minute limit, so a controls layer should not copy it.<Cite ids="clm-visa-tap-088 clm-visa-tap-100" />
- **At settlement.** Issuer and network risk decisions apply to the token, and Visa says TAP feeds telemetry into its fraud and risk models.<Cite ids="clm-visa-tap-122" />
- **After the fact.** VIC confirmations and commerce signals support disputes.<Cite ids="clm-visa-tap-130" /> TAP has no revocation list or key status endpoint.<Cite ids="clm-visa-tap-128" />

## What is observable from outside

The JWKS the specification used to name is public and cacheable for an hour, so anyone can watch keys appear or disappear there.<Cite ids="clm-visa-tap-073" /> Visa newsroom releases name adopting merchants and issuers with dates.<Cite ids="clm-visa-tap-160 clm-visa-tap-180" /> Everything else is private. TAP is off-chain and defines no events or explorers.<Cite ids="clm-visa-tap-132" /> Signature headers reach only the CDN, the merchant and the path between them.<Cite ids="src-visa-tap-spec" /> On Cloudflare the zone owner can read `cf.bot_management.signed_agent` for Web Bot Auth agents, which needs an Enterprise plan with Bot Management; whether TAP results appear there is not documented.<Cite ids="clm-visa-tap-134" /> The consumer object sends the consumer's IP address, device data, country and postal code to the merchant.<Cite ids="clm-visa-tap-136" />

## What can go wrong

- **Untagged request.** Without a TAP tag the request was not signed by a trusted agent; the merchant treats it as any other bot.<Cite ids="clm-visa-tap-041" />
- **Stale or replayed signature.** A bad window, a reused nonce, a missing key or a failed signature each lead to a block.<Cite ids="clm-visa-tap-076" /> A checkout signed before a slow passkey approval can outlive its window and then needs a fresh signature.
- **Unresolvable key.** With only an RSA sandbox key at the URL the specification used to name, a verifier that relies on it cannot check an Ed25519 signature like the specification's examples.<Cite ids="clm-visa-tap-071 clm-visa-tap-044" />
- **Tampered body.** The minimum header signature does not cover the body.<Cite ids="clm-visa-tap-095" /> A payment container that fails its checks should not be used for payment.<Cite ids="clm-visa-tap-081" /> A consumer object that fails may still be used, at the merchant's risk.<Cite ids="clm-visa-tap-080" />
- **Who bears the loss.** Worldpay wrote that no liability shift for agentic transactions exists yet.<Cite ids="clm-visa-tap-169" /> It says fraud on properly authenticated, correctly tokenized agent transactions generally follows existing tokenized-transaction rules, while disputes short of fraud remain unsettled.<Cite ids="clm-visa-tap-170" /> Visa's rules govern Visa and its member institutions and yield to applicable law. Within Visa's system, they make the cardholder responsible for what an Agentic Payment Provider does in an Agentic Transaction, as if the cardholder had initiated it. Visa calls none of its agent rules a liability shift.<Cite ids="clm-visa-tap-171" /> Issuers must pay for Agentic Transactions made under the cardholder's payment instructions, and from 2026-10-24 a provider's login ID can help defeat a card-absent fraud dispute.<Cite ids="clm-visa-tap-238" />

## Variants

- **Encrypted payload instead of key entry.** A merchant that onboards its public key to the scheme can receive an encrypted payload holding the token, expiry, cardholder name and dynamic data.<Cite ids="clm-visa-tap-231 clm-visa-tap-061" /> No form fill is needed.
- **Pay-per-access with a browsing IOU.** When the merchant answers with HTTP 402, the container can carry a `browsingIOU` instead.<Cite ids="clm-visa-tap-063" /> TAP defines neither the 402 format nor how the IOU is settled.<Cite ids="clm-visa-tap-084" />
