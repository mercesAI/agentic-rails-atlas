## Identity and governance

- **What it is.** x402 is an open payment standard that uses the HTTP `402 Payment Required` status code so a client can pay for a resource inside a normal request and response cycle. The repository describes it as "an open standard for internet native payments" that aims to support crypto and fiat networks (`research/vendor/x402/README.md`) [src-x402-repo].
- **Origin.** Coinbase Developer Platform. The whitepaper "x402: An open standard for internet-native payments" is credited to Erik Reppel, Ronnie Caspers, Kevin Leffew, Danny Organ, Dan Kim and Nemil Dalal, "Coinbase Developer Platform / x402", and is dated May 6, 2025 (text extracted from the PDF at https://x402.org/x402-whitepaper.pdf, 995,488 bytes, HTTP `Last-Modified` 2026-07-02) [src-x402-whitepaper]. The legacy npm package `x402` was created 2025-02-20 and version 0.3.0 was published 2025-05-06, the launch day [src-x402-npm-legacy]. Secondary coverage names AWS, Circle, Anthropic and NEAR (one account names the MCP project instead of NEAR) as launch collaborators; the Coinbase launch page itself returned HTTP 403 and the archived copy could not be fetched, so the partner list is reported, not verified [src-x402-launch-coverage].
- **Repository lineage.** The GitHub repository `x402-foundation/x402` was created 2025-02-21 (it is the original `coinbase/x402` repository, transferred; GitHub repository id 936374955). The `x402-foundation` organization was created 2026-04-01. `coinbase/x402` now exists as a fork of `x402-foundation/x402`, created 2026-04-02 [src-x402-gh-repo] [src-x402-gh-fork]. The organization also holds `tsc`, `wg-identity`, `wg-tax`, `wg-domain-discovery`, `wg-card-acceptance` and `foundation` repositories [src-x402-gh-org].
- **Legal entity and charter.** The technical charter PDF in `research/vendor/x402/foundation/x402 Technical Charter March 31, 2026.pdf` is titled "Technical Charter for x402 a Series of LF Projects, LLC", "Adopted March 31, 2026". It establishes a Technical Steering Committee (TSC) of Representatives of Participating Organizations, one vote per Representative, majority decisions, a 75 percent Supermajority Vote for changes to the Core Principles or removal of a Participating Organization, and a 10 business day voting window. It references the project principles at `https://github.com/coinbase/x402?tab=readme-ov-file#principles` [src-x402-charter]. The PDF was added by PR #1911, merged 2026-04-02 [src-x402-gh-pr-1911].
- **TSC roster.** `research/vendor/x402/TSC.md` lists, in seniority order: Coinbase, Inc. (Erik Reppel), Cloudflare, Inc. (Rohin Lohe), Stripe, Inc. (Steve Kaliski). The file was created by PR #2253 "Create TSC.md", merged 2026-05-12 [src-x402-tsc] [src-x402-gh-pr-2253]. The seed calls this a "steering committee"; the charter and file call it the Technical Steering Committee.

## Actors and roles

From `research/vendor/x402/README.md` ("Terms") and `specs/x402-specification-v2.md` section 3 [src-x402-repo] [src-x402-spec-v2]:

| Role | Definition in the files | Notes |
| --- | --- | --- |
| `client` | "An entity wanting to pay for a resource." Any application or agent requesting a protected resource. | Signs the payment authorization. SDK `x402Client` applies `spendControls` and policies before selecting an `accepts[]` entry. |
| `resource server` | "An HTTP server that provides an API or other resource for a client." | Emits `PaymentRequired`, calls facilitator `/verify` and `/settle` (or verifies locally), serves the resource. |
| `facilitator` | "A server that facilitates verification and execution of payments for one or many networks." | Verifies signatures and state, broadcasts transactions, usually pays gas. "The facilitator does not hold funds or act as a custodian" (`docs/core-concepts/facilitator.md`). Anyone can run one; self-facilitation inside the resource server is supported (`examples/typescript/servers/self-facilitation`). |
| `resource` | "Something on the internet": a web page, API, RPC service, file. | Described by `ResourceInfo`. |
| Sponsor / fee payer (SVM) | `scheme_exact_svm.md`: the entity that signs as `feePayer`; may be the merchant or a third party facilitator. | Advertised in `extra.feePayer`. |
| Receiver authorizer, payer authorizer (batch-settlement EVM) | Addresses in `ChannelConfig` that authorize claims and refunds (receiver side) or sign vouchers (payer side). | May be delegated to a facilitator. |
| Operator (auth-capture EVM) | `paymentInfo.operator` on the `AuthCaptureEscrow` contract; `extra.operatorType` is `"delegated"` (facilitator is operator) or `"custom"`. | |
| Network (credit-backed batch-settlement) | For `cloudflare:402` the network itself acts as Merchant of Record and bills the signature agent's identity. | `payTo` is the constant `"merchant"`. |
| Bazaar / discovery service | Facilitator-side catalog of resources advertising the `bazaar` extension. | CDP Bazaar is public without an API key. |

Principles in the README that constrain roles: "Trust minimizing: all payment schemes must not allow for the facilitator or resource server to move funds, other than in accordance with client intentions"; client and server "should not need to think about gas, rpc, etc." [src-x402-repo].

### Facilitator request body (`POST /verify` and `POST /settle`) : section 7.1

`{ "x402Version": 2, "paymentPayload": PaymentPayload, "paymentRequirements": PaymentRequirements }`. For `upto`, `paymentRequirements.amount` is the ceiling at verify time and the actual charge at settle time.

### Discovery resource (`GET /discovery/resources`) : section 8.3

`resource` (string, Required), `type` (string, Required, currently `"http"`), `x402Version` (number, Required), `accepts` (array, Required), `lastUpdated` (ISO 8601 string, Required), `extensions` (object, Optional). Query params: `type`, `payTo`, `scheme`, `network`, `extensions`, `limit` (1 to 100, default 20), `offset`.

### V1 objects for contrast : `specs/x402-specification-v1.md`

## Message flows step by step (happy path and failures)

### Flow A: V2 HTTP, `exact`, `authorization` payment flow (default)

Defined in `README.md` ("Typical x402 flow"), `specs/transports-v2/http.md` and `specs/x402-specification-v2.md` sections 2, 6.1 and 7 [src-x402-repo] [src-x402-transport-http-v2] [src-x402-spec-v2].

| # | From | To | What is sent | What can fail |
| --- | --- | --- | --- | --- |
| 1 | Client | Resource server | Plain HTTP request, no `PAYMENT-SIGNATURE` header | Optional step if client already knows the price |
| 2 | Resource server | Client | `402 Payment Required`, header `PAYMENT-REQUIRED` = base64 `PaymentRequired { x402Version: 2, error, resource, accepts[], extensions }`; body is a server concern | Server misconfiguration: since `@x402/core` 2.25.0 a route with no registered scheme throws instead of sending an empty `accepts` |
| 3 | Client | (local) | Selects one `accepts[]` entry; spendControls reject unknown assets or amounts above the cap (default `$1`); builds `PaymentPayload` and signs EIP-712 `TransferWithAuthorization { from, to, value, validAfter, validBefore, nonce }` | All entries rejected by `spendControls`; unknown `paymentFlow` entries must be skipped |
| 4 | Client | Resource server | Same request plus `PAYMENT-SIGNATURE` = base64 `PaymentPayload { x402Version, resource, accepted, payload, extensions }` | Header over 2 KB may be dropped by intermediaries (noted in Cloudflare binding); malformed header gives `400` (`invalid_payload`) |
| 5 | Resource server | Facilitator | `POST /verify` with `{ x402Version, paymentPayload, paymentRequirements }` | Facilitator timeout (`FacilitatorTimeoutError`, surfaced as 502, default 30 s TS, 90 s Python); facilitator down |
| 6 | Facilitator | Resource server | `VerifyResponse { isValid, invalidReason?, payer }` after signature recovery, balance check, amount and window checks, token and network match, simulation | `insufficient_funds`, `invalid_exact_evm_payload_signature`, `invalid_exact_evm_payload_authorization_valid_before`, `..._valid_after`, `..._value_mismatch`, `..._recipient_mismatch`, `invalid_network`, `invalid_scheme`, `unsupported_scheme`, `invalid_x402_version`, `unexpected_verify_error` |
| 7 | Resource server | (local) | If `isValid` is false: `402` with a fresh `PAYMENT-REQUIRED` (and `PAYMENT-RESPONSE` failure). If true: executes the handler | Handler failure: client is not charged under `authorization` (`settleOnCancel` hook available) |
| 8 | Resource server | Facilitator | `POST /settle` with the same body | Timeout is indeterminate: settlement may still have happened |
| 9 | Facilitator | Chain | Broadcasts `transferWithAuthorization` (or proxy `settle`, or `redeemDelegations`), waits for receipt (`confirmationTimeoutMs` default 180,000 ms in TS) | Nonce already consumed, RPC error |
| 10 | Facilitator | Resource server | `SettleResponse { success, transaction, network, payer, amount?, errorReason? }` | `settlement_pending` (non terminal, carries tx hash; server retries once and reconciles via `PendingSettlementStore`), `invalid_transaction_state`, `unexpected_settle_error` |
| 11 | Resource server | Client | `200 OK` with resource body and `PAYMENT-RESPONSE` = base64 `SettleResponse`; on failure `402` with `PAYMENT-RESPONSE` carrying `success: false`; `Cache-Control: no-store` on 402, `private` on 200 (SDK 2.21.0) | Client receives resource but settlement reported pending |

### Flow B: `upfront` payment flow (settle before resource)

Used by `exact` where the network has no pull primitive (Lightning `lnbtc`, client submitted proofs). Ordering: settle, resource, respond. `/verify` is not called. For `lnbtc`: server mints a fresh BOLT11 invoice with description hash = request hash and returns it in `extra.invoice`; client pays and returns the preimage; facilitator checks `SHA-256(preimage) == payment_hash`, checks the invoice signing key equals `payTo`, atomically records the payment hash in a replay store, then the server serves the resource. Failures: expired invoice (`maxTimeoutSeconds` equals invoice expiry), preimage mismatch, replayed payment hash, unmet finality. No refund path is defined (`specs/schemes/exact/scheme_exact_lnbtc.md`, `specs/schemes/exact/scheme_exact.md`).

### Flow C: `escrow` payment flow (settle, resource, settle)

Default for `auth-capture` and for SVM `upto`. First `/settle` places a hold (`authorize`) or opens a channel; the resource runs; a second `/settle` captures the actual amount or voids. A scheme defining multiple settles must let the facilitator distinguish them (server led, for example `payload.type`). Invariant from section 6.1: at least one verify or settle MUST run before the resource executes.

### Flow D: `upto` on EVM

Client signs Permit2 `permitWitnessTransferFrom` with `permitted.amount` = ceiling and `witness { to, facilitator, validAfter }`; `/verify` checks `permitted.amount == requirements.amount`, Permit2 allowance (else `412 Precondition Failed`, code `PERMIT2_ALLOWANCE_REQUIRED`), balance, `deadline`, simulation. At `/settle` the server sets `paymentRequirements.amount` to the metered charge; the facilitator re-verifies the signature against `permitted.amount`, checks charge <= ceiling (else `invalid_upto_evm_payload_settlement_exceeds_amount`), calls `x402UptoPermit2Proxy.settle` for the actual amount; a zero charge needs no transaction (`specs/schemes/upto/scheme_upto_evm.md`).

### Flow E: `batch-settlement` on EVM (payment channels)

Commit, accumulate, redeem. Deposit (`payload.type: "deposit"`, gasless via `ERC3009DepositCollector` or `Permit2DepositCollector`) creates a channel whose `channelId = EIP712Hash(ChannelConfig)`; each request carries a cumulative voucher (`maxClaimableAmount = chargedCumulativeAmount + amount`); server verifies the signature off chain and serves immediately; a channel manager later calls `claimWithSignature` (updates `totalClaimed`) and `settle` (one token transfer sweeping many claims); refunds via `refund` or `refundWithSignature`; client escape hatch `initiateWithdraw` then `finalizeWithdraw` after `withdrawDelay` (15 minutes to 30 days). Failures use codes such as `invalid_batch_settlement_evm_channel_id_mismatch`, `..._cumulative_below_claimed`, `..._cumulative_exceeds_balance`, `..._deposit_below_min_deposit` (`specs/schemes/batch-settlement/scheme_batch_settlement_evm.md`).

### Flow F: `batch-settlement` on `cloudflare:402` (credit backed)

Client hosts keys at `/.well-known/http-message-signatures-directory`, registers the signature agent with Cloudflare via `registrationUrl`, then signs each request with RFC 9421 (`Signature-Agent`, `Signature-Input`, `Signature`, covering `@authority`, `signature-agent`, `payment-signature`) and includes `PAYMENT-SIGNATURE` with `payload { amount, asset }`, `payTo: "merchant"`, `asset: "USD"`. Verification is stateless; Cloudflare bills the identity later. Error codes: `blocked`, `price_not_acceptable`, `payment_failed`, `invalid_signature`, `signature_agent_unknown`, `invalid_payment_signature`, `origin_error`, `unknown` (`specs/schemes/batch-settlement/scheme_batch_settlement_cloudflare.md`).

### Flow G: V1 HTTP (for contrast)

`402` with a JSON body `PaymentRequirementsResponse`; client retries with header `X-PAYMENT` (base64 `PaymentPayload { x402Version: 1, scheme, network, payload }`); server returns `X-PAYMENT-RESPONSE`. Networks are strings (`base-sepolia`, `base`, `avalanche-fuji`, `avalanche`, `iotex`), the price field is `maxAmountRequired` (`specs/transports-v1/http.md`, `specs/x402-specification-v1.md`, `docs/guides/migration-v1-to-v2.mdx`).

### Flow H: MCP transport (V2)

Paid tool call without payment returns a tool result with `isError: true`, `structuredContent` = `PaymentRequired` and `content[0].text` = the same JSON string; client retries with `_meta["x402/payment"]` = `PaymentPayload`; server returns `_meta["x402/payment-response"]` = `SettleResponse`. If settlement fails after execution the tool content must not be returned (`specs/transports-v2/mcp.md`).

### Flow I: A2A transport (V2)

Task in state `input-required` with message metadata `x402.payment.status: "payment-required"` and `x402.payment.required` = `PaymentRequired`; client sends `message/send` with `taskId`, `x402.payment.status: "payment-submitted"`, `x402.payment.payload`; server completes with `x402.payment.status: "payment-completed"` and `x402.payment.receipts[]` (array of `SettleResponse`), or fails with `payment-failed` and `x402.payment.error` (for example `EXPIRED_PAYMENT`, `INSUFFICIENT_FUNDS`). Agents declare the extension in `AgentCard.capabilities.extensions[].uri` and clients activate it with the `X-A2A-Extensions` header (`specs/transports-v2/a2a.md`).

## State machines

### Payment flow orderings (`specs/x402-specification-v2.md` section 6.1)

| `extra.paymentFlow` | States in order | Trigger to advance |
| --- | --- | --- |
| `authorization` (default) | requested, verified (`/verify`), executed (handler), settled (`/settle`), responded | each facilitator call succeeding; `/verify` is read only |
| `upfront` | requested, settled (`/settle`), executed, responded | settle success establishes validity; no `/verify` |
| `escrow` | requested, deposit settled (`/settle` 1), executed, final charge settled (`/settle` 2), responded | first settle is the pre-resource check |

Rules: when the resolved flow is not `authorization`, `accepts[].extra.paymentFlow` MUST be present; clients MUST NOT build a payment for an unrecognized flow; servers MUST reject unsupported method and flow pairs; clients SHOULD prefer `authorization` when both are offered.

### HTTP response states (`specs/transports-v2/http.md`)

Payment Required: 402. Invalid Payment: 400. Payment Failed: 402. Server Error: 500. Success: 200. Permit2 allowance missing: 412 (`scheme_exact_evm.md`).

### A2A payment status lifecycle (`specs/transports-v2/a2a.md`, "Payment Status Lifecycle")

| `x402.payment.status` | Task state | Transition |
| --- | --- | --- |
| `payment-required` | `input-required` | server sends requirements |
| `payment-rejected` | `failed` or `input-required` | client declines |
| `payment-submitted` | `input-required` to `working` | client sends payload |
| `payment-verified` | `working` | server verifies |
| `payment-completed` | `working` to `completed` | settlement succeeds |
| `payment-failed` | `failed` | verify or settle fails |

### `auth-capture` payment lifecycle (`specs/schemes/auth-capture/scheme_auth_capture.md`)

Operations and repeatability: `authorize` (once), `charge` (once, no hold), `capture` (repeatable up to the hold), `void` (once while a hold remains), `refund` (repeatable up to captured minus refunded), `reclaim` (client only, after `extra.captureDeadline`). Under `escrow`: authorize, then capture or void, then refund, or reclaim after the capture deadline. Under `authorization`: charge then refund. `extra.refundDeadline` bounds refunds. Default flow is `escrow`; EVM default deployment is base/commerce-payments v1.1 `AuthCaptureEscrow`.

### `batch-settlement` EVM channel states (`specs/schemes/batch-settlement/scheme_batch_settlement_evm.md`)

Channel created on first deposit (`ChannelCreated`), funded (`Deposited`), vouchers accumulate off chain, claimed (`Claimed`, updates `totalClaimed`), settled (`Settled`, token transfer), refunded (`Refunded`), withdrawal pending (`WithdrawInitiated`, after `initiateWithdraw`), withdrawn (`WithdrawFinalized`), closed (`ChannelClosed` when unclaimed escrow returns to zero with `totalClaimed == 0`). `ChannelCreated` can fire again if a drained channel is re-funded.

### Settlement outcome states (`specs/x402-specification-v2.md` section 9, `docs/core-concepts/facilitator.md`)

`success: true`; `success: false` terminal (`errorReason` set, `transaction` empty); `success: false` with `errorReason: "settlement_pending"` (non terminal, `transaction` non empty, server retries exactly once and reconciles through `PendingSettlementStore`). Solana duplicate submissions are blocked by a 120 second in-memory `SettlementCache`.

## Cryptography and standards used

- **EIP-712 typed data** for every EVM signature: `TransferWithAuthorization(address from,address to,uint256 value,uint256 validAfter,uint256 validBefore,bytes32 nonce)` for `exact` with `eip3009`; Permit2 `PermitWitnessTransferFrom` with witness type string `"Witness witness)TokenPermissions(address token,uint256 amount)Witness(address to,uint256 validAfter)"` for `exact` Permit2; batch-settlement `Voucher`, `Refund`, `ClaimBatch` under the `x402 Batch Settlement` domain; offer and receipt signatures under domains `"x402 offer"` and `"x402 receipt"` with `chainId` 1 (`specs/x402-specification-v1.md` 6.1.1, `specs/schemes/exact/scheme_exact_evm.md`, `scheme_batch_settlement_evm.md`, `extension-offer-and-receipt.md`).
- **EIP-3009** `transferWithAuthorization` (exact, default on EVM) and `receiveWithAuthorization` (deposit collector and auth-capture collector). **EIP-2612** permits for gasless Permit2 approvals. **Uniswap Permit2** `permitWitnessTransferFrom` through `x402ExactPermit2Proxy` (`0x402085c248EeA27D92E8b30b2C58ed07f9E20001`) and `x402UptoPermit2Proxy` (`0x4020A4f3b7b90ccA423B9fabCc0CE57C6C240002`), both CREATE2 at the same address on every chain. **ERC-7710** delegation (`redeemDelegations`) with **ERC-7715** as one way to obtain a delegation. **ERC-1271** and **ERC-6492** smart wallet signatures (changelog 2.x). **ERC-8021** Schema 2 (CBOR) builder codes appended to settlement calldata. **EIP-1153** transient storage reentrancy guard in `x402BatchSettlement`.
- **CAIP-2** network ids (`eip155:8453`, `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp`, `stellar:pubnet`, `lnbtc:000000000019d6689c085ae165831e93`, `tvm:-239`, `algorand:...`, `aptos:1`, `hedera:mainnet`, `keeta:21378`, `near:mainnet`, `ccd:...`, `xrpl:0`, `cardano:mainnet`); the spec encourages the same shape for non blockchain rails and gives `ach:us` and `sepa:eu` only as examples (`specs/x402-specification-v2.md` 11.1; `docs/core-concepts/network-and-token-support.mdx`). **CAIP-122** for Sign-In-With-X (EIP-191 on EVM, Ed25519 on Solana).
- **Solana**: partially signed versioned transactions, `TransferChecked` on `spl-token` or `token-2022`, facilitator co-signs as `feePayer`; Ed25519.
- **Lightning**: BOLT11 invoices, SHA-256 preimage proofs, secp256k1 node keys in `payTo`, JSON Canonicalization Scheme (RFC 8785) for the request hash, BIP-122 style CAIP-2 references.
- **HTTP Message Signatures (RFC 9421)** with Ed25519 and the `web-bot-auth` tag, key directories per `draft-meunier-http-message-signatures-directory-04`, for `cloudflare:402` and the `http-message-signatures` extension; optional server signed responses covering `@status` and `payment-response`.
- **JWS compact serialization** (`ES256K`, `EdDSA`, `kid` as DID URL) as the alternative receipt format; **JSON Schema 2020-12** for extension `schema` objects; **base64** header encoding; **ISO 4217** fiat asset codes.
- Other chain primitives named in `scheme_exact_*.md`: Stellar SEP-41 and CAP-71 Soroban auth entries, TON W5 wallets and TEP-74 jettons, Algorand `axfer` atomic groups, Aptos `primary_fungible_store::transfer`, Hedera `cryptoTransfer`, NEAR NEP-366 `SignedDelegate` over NEP-141 `ft_transfer`, Starknet SNIP-9 and SNIP-12, XRPL `Payment` with `sequence` or `ticketSequence`, Cardano native tokens, Casper CEP-3009, Concordium sponsored transfers.

## Security model and published attacks or CVEs

**What the protocol itself guarantees (spec text).**
- The client signature binds amount and recipient: `authorization.to` and `authorization.value` are inside the signed EIP-712 struct; for Permit2 the proxy forces `transferDetails.to = witness.to` and the facilitator "cannot modify the amount or destination. They serve only as the transaction broadcaster" (`specs/schemes/exact/scheme_exact_evm.md`). `upto` adds `witness.facilitator` so only the announced facilitator can settle.
- Replay protection: a 32 byte random `nonce` that EIP-3009 contracts refuse to reuse, plus `validAfter` and `validBefore` windows (`specs/x402-specification-v2.md` 10.1). Permit2 nonces for `upto`; monotonic cumulative vouchers and per channel `refundNonce` for batch-settlement; atomic replay stores keyed by CAIP-2 network plus payment hash for client submitted proofs (`scheme_exact.md`, `scheme_exact_lnbtc.md`).
- `/verify` is read only and MUST NOT write state; the resource never executes with nothing checked (section 6.1 invariant).
- Facilitator safety rules per network: the fee payer must not appear in sensitive instructions or be debited beyond the fee (SVM, Stellar, Hedera, Starknet, TON lists in `scheme_exact.md`); exactly one identifiable transfer of `amount` to `payTo` must result; duplicate delivery must be deduplicated atomically across every `/settle` process.
- `exact` is final: "this specification defines no refund, and any remedy is the resource server's own arrangement" (`scheme_exact.md`). Refunds exist only in `auth-capture` (`refund`, `void`, `reclaim`) and in batch-settlement channels (`refund`, timed withdrawal), or through third parties such as x402r (`docs/dev-tools/third-party-extensions.md`).
- Trust assumptions stated in the specs: `upto` requires clients to trust servers to charge fairly up to the ceiling; `cloudflare:402` is "credit-backed" with Cloudflare as Merchant of Record; `upfront` leaves a client charged if the handler fails; facilitators are a shared trust point (the facilitator can refuse but cannot redirect funds).
- SDK level mitigations: `spendControls` (default assets only, `$1` per payment cap, `DEFAULT_MAX_AMOUNT_PER_PAYMENT = "$1"` in `typescript/packages/core/src/client/x402Client.ts`), SIWX origin binding before signing, `Cache-Control: no-store`, route matching hardening against percent encoding and backslashes, `SettlementCache` against Solana duplicate settlement, `PendingSettlementStore` reconciliation, explicit gas limits and simulation for ERC-7710.

**Published advisories.** GHSA-3j63-5h8p-gf7c (2025-08-20, high, legacy npm packages < 0.5.2, resource server builders) and GHSA-qr2g-p6q7-w82m (2026-03-07, high, Solana facilitators; `@x402/svm` < 2.6.0, PyPI `x402` < 2.3.0, Go < 2.5.0). No CVE identifiers were assigned to either [src-x402-ghsa-2025] [src-x402-ghsa-2026]. Three Cantina audit reports (February, March, May 2026) ship in `contracts/evm/audits/`. The repository `SECURITY.md` still routes reports to Coinbase's HackerOne program [src-x402-repo].

**Academic attack literature (titles verified against arXiv, see Publications).**
- arXiv:2605.11781 "Five Attacks on x402 Agentic Payment Protocol" (Li, Wang, Wang; 2026-05-12): five practical attacks on authorization, binding, replay protection and web layer handling, validated on local chains, Base Sepolia and live endpoints, with audits of three open source SDKs.
- arXiv:2607.19545 "When HTTP 402 Meets the Blockchain: Risks on Emerging x402 Payments" (Wang et al.; 2026-07-21): first systematic study of facilitator mediated deployments, eight security rules for facilitators, four new attack vectors. The seed's "all 15 tested facilitators violated at least one rule" is not visible in the abstract and remains unconfirmed.
- arXiv:2605.30998 "Free-Riding the Agentic Web: A Systematic Security Analysis of x402 Payments" (Ling et al.; 2026-05-29): four flaw classes including cross resource substitution and a duplicate settlement race, organized around five invariants.
- arXiv:2603.01179 "A402: Binding Cryptocurrency Payments to Service Execution for Agentic Commerce" (Li et al.; 2026-03-01): argues x402 does not enforce atomicity across execution, payment and delivery; proposes Atomic Service Channels with TEE assisted adaptor signatures.
- arXiv:2604.11430 "Hardening x402: PII-Safe Agentic Payments via Pre-Execution Metadata Filtering" (Stantchev; 2026-04-13): PII leakage through `resource` metadata sent to servers and facilitators; middleware with PII redaction and spending policies.
- arXiv:2609.00060 "A Formal Analysis of Agent Payment Protocols" (Jiang et al.; 2026-08-30): Tamarin models of x402, MPP, ACP and AP2.

## Observability (public versus private data, exact events, endpoints and documents)

**Public, on chain.**
- `exact` with `eip3009`: the token's own `Transfer` and EIP-3009 `AuthorizationUsed` events; nothing marks an x402 payment as such on chain, which is why arXiv:2607.12575 resolves payers through the meta transaction layer and why `erc-8004-best-practices/Reputation.md` notes that indexers cannot easily distinguish generic transfers from x402 payments.
- Permit2 proxies: `event x402PermitTransfer(address from, address to, uint256 amount, address asset)` (spec listing in `scheme_exact_evm.md`); the deployed `x402BasePermit2Proxy.sol` declares `Settled()`, `SettledWithPermit()`, `EIP2612PermitFailedWithReason(address indexed token, address indexed owner, string reason)`, `EIP2612PermitFailedWithPanic(...)`, `EIP2612PermitFailedWithData(...)` (`contracts/evm/src/x402BasePermit2Proxy.sol`).
- `x402BatchSettlement.sol` events: `ChannelCreated(bytes32 indexed channelId, ChannelConfig config)`, `ChannelClosed(bytes32 indexed channelId, ChannelConfig config)`, `Deposited(bytes32 indexed channelId, address indexed sender, uint128 amount, uint128 newBalance)`, `Claimed(bytes32 indexed channelId, address indexed sender, uint128 claimAmount, uint128 newTotalClaimed)`, `Settled(address indexed receiver, address indexed token, address indexed sender, uint128 amount)`, `Refunded(bytes32 indexed channelId, address indexed sender, uint128 amount)`, `WithdrawInitiated(bytes32 indexed channelId, uint128 amount, uint40 finalizeAfter)`, `WithdrawFinalized(bytes32 indexed channelId, address indexed sender, uint128 amount)` (`contracts/evm/src/x402BatchSettlement.sol`).
- Canonical contract addresses (same on every supported EVM chain): `x402ExactPermit2Proxy` `0x402085c248EeA27D92E8b30b2C58ed07f9E20001`; `x402UptoPermit2Proxy` `0x4020A4f3b7b90ccA423B9fabCc0CE57C6C240002`; `x402BatchSettlement` `0x4020074e9dF2ce1deE5A9C1b5c3f541D02a10003`; `ERC3009DepositCollector` `0x4020806089470a89826cB9fB1f4059150b550004`; `Permit2DepositCollector` `0x4020425FAf3B746C082C2f942b4E5159887B0005`. Batch settlement is listed as deployed on Base, Arbitrum, World Chain (and Sepolia), Polygon, Optimism, Avalanche, Celo, Linea, Unichain and Monad mainnets (`contracts/evm/README.md`).
- Builder codes: ERC-8021 suffix in settlement calldata lets indexers attribute app, facilitator and client.
- Solana: optional Memo instruction carrying `extra.memo` for reconciliation.

**Public, HTTP.**
- Facilitator `GET /supported`. The public testnet facilitator `https://x402.org/facilitator/supported` returned (2026-10-10) kinds for `exact`, `upto` and `batch-settlement` on `eip155:84532`, `exact` on Solana devnet, Algorand testnet, `aptos:2`, `stellar:testnet`, `hedera:testnet`, `xrpl:1`, plus V1 `base-sepolia` and `solana-devnet`; extensions `builder-code`, `eip2612GasSponsoring`, `erc20ApprovalGasSponsoring`; signers `eip155:*` `0xd407e409E34E0b9afb99EcCeb609bDbcD5e7f1bf`, `solana:*` `CKPKJWNdJEqa81x7CkZ14BVPiY6y16Sxs7owznqtWYp5` [src-x402-facilitator-supported].

- Other community directories named in the README: Agentic.Market, Pay.sh, app.ampersend.ai/discover, x402-list.com.

**Private or off chain.**
- `PAYMENT-REQUIRED`, `PAYMENT-SIGNATURE` and `PAYMENT-RESPONSE` header contents (including `resource.url`, descriptions and amounts) travel only between client, server and facilitator; arXiv:2604.11430 treats this metadata as a PII channel.
- Facilitator logs, KYT or OFAC decisions, `PendingSettlementStore`, `SettlementCache`, Bazaar crawl state.
- Batch-settlement vouchers and `chargedCumulativeAmount` live in server storage until claimed; only claims, settles and refunds reach the chain. Credit backed `cloudflare:402` commitments never reach a chain; billing identity mapping is Cloudflare's.
- Who controls a paying wallet is not visible on chain (the basis of the volume authenticity dispute).

## Compliance touchpoints

- The protocol has no built in KYC, KYA or sanctions layer; it moves signed authorizations for stablecoins or fiat units. The repository frames compliance as a facilitator concern, and the CDP facilitator advertises OFAC and KYT screening on every transaction [src-x402-cdp-facilitator].
- Fiat and credit backed rails exist in the spec (`asset` as ISO 4217 code, `payTo: "merchant"`, `cloudflare:402` billing by identity), which places Cloudflare as Merchant of Record with its own terms, billing periods and dispute handling outside the protocol (`scheme_batch_settlement_cloudflare.md`).
- Identity hooks: `sign-in-with-x` (wallet proof of control), `auth-hints` (OAuth 2.0 with DPoP, RFC 7591 dynamic registration), RFC 9421 Web Bot Auth identities, the x402 Foundation working groups `wg-identity`, `wg-tax`, `wg-card-acceptance` (repository names only) [src-x402-gh-org].
- The Technical Charter allows removal of a Representative or Participating Organization "if the same is directed by any regulator with jurisdiction over the Project" [src-x402-charter].
- Geographic gating appears in products built on x402: Cloudflare Monetization Gateway closed beta is limited to "eligible U.S.-based sellers and buyers" [src-x402-cf-mg-beta]; Stripe's machine payments preview was reported as US businesses only [src-x402-stripe-coverage].
- Tax: `wg-tax` working group exists; no spec content yet.
- Data protection: payment metadata (`resource.url`, `description`) is sent to facilitators that may not have data processing agreements with the payer (arXiv:2604.11430).
- Receipts for audit: `offer-receipt` extension and `SettleResponse.transaction`; Stripe's integration reportedly maps settlements onto PaymentIntents for tax, refunds and reporting [src-x402-stripe-coverage].

## Criticisms and open questions

- **Volume authenticity.** Raw counters (x402.org, CDP "100M+") are contested: Artemis adjusted $135.7M and 178.3M operations down to $15.0M and 109.6M (to 2026-04-21); Artemis "Gamed Tx" averaged 63.94 percent of transactions in winter 2025 to 2026; arXiv:2607.12575 argues settlement counts are the one metric an interested party can manufacture almost for free because the facilitator pays gas and nothing on chain marks who controls a payment. The x402.org 30 day counter has shown the same $24.24M figure from mid August to 2026-10-10.
- **Facilitator centralization.** The protocol is permissionless but CDP processes the bulk of payments, screens with KYT and OFAC, and Cloudflare's gateway routes through Coinbase's facilitator; arXiv:2607.19545 frames facilitators as shared infrastructure where one flaw hits many merchants.
- **No refunds in `exact`.** Finality is a feature for sellers and a gap for buyers; `auth-capture` (2026-05-13) and third party x402r are the answers, with limited SDK coverage (no Python auth-capture).
- **Payment and service are not atomic.** A402 (arXiv:2603.01179) and the free riding paper (arXiv:2605.30998) show unpaid service or paid non delivery paths; `upfront` shifts risk to the buyer, `authorization` to the seller.
- **Header size.** Base64 JSON in headers can exceed 2 KB; Cloudflare strips `schema` and optional fields to fit.
- **Spec drift and naming.** `deferred` to `batch-settlement`; leftover `deferred` examples in `auth-hints`; `SettleResponse` versus `SettlementResponse`; a `2025-04-28` date in the batch-settlement EVM version table; the A2A extension URI differs between the x402 transport spec (v0.1) and the a2a-x402 repo (v0.2).
- **Breadth versus parity.** 13 network families in TypeScript but only 2 to 3 in Go and Python; `offer-receipt` TypeScript only; Java unpublished.
- **Metadata privacy.** `resource.url` and descriptions reach facilitators without data processing agreements (arXiv:2604.11430).
- **Governance questions.** TSC is three companies (Coinbase, Cloudflare, Stripe) with seniority ordering; Premier membership at $200,000 per secondary reporting; Stripe sits on both x402 and MPP.
- **Open items to track.** Does the x402.org counter resume updating; publication of Cloudflare's programmatic registration API for `cloudflare:402`; Python support for `auth-capture` and SVM `batch-settlement`; whether `x402-a2a` reaches PyPI; CVE assignment for the two GHSA advisories.
