## Actors and roles

| Actor | What it does | Spec reference |
|---|---|---|
| Agent owner | Holds the ERC-721 token for an `agentId`; can transfer it, set `agentURI`, set metadata, set or unset `agentWallet`, request validation | Identity Registry [src-erc-8004-spec] |
| Operator | An address approved by the owner through ERC-721 `approve` or `setApprovalForAll`; can set the URI, metadata and wallet and request validation like the owner (transfer follows ERC-721 approval rules); cannot give feedback to the agent | [src-erc-8004-spec] [src-erc-8004-identity-sol] |
| Agent wallet | The address in the reserved `agentWallet` key where the agent "receives payments"; defaults to the owner at registration; changing it needs a signature from the new wallet | [src-erc-8004-spec] |
| Client (`clientAddress`) | Any address that calls `giveFeedback`; when the client is itself an agent it SHOULD use its `agentWallet` | [src-erc-8004-spec] |
| Responder | Anyone who calls `appendResponse` (the spec gives the agent showing a refund and a spam-tagging aggregator as examples) | [src-erc-8004-spec] |
| Validator (`validatorAddress`) | A contract or address named in `validationRequest` that alone may call `validationResponse` for that `requestHash` | [src-erc-8004-spec] [src-erc-8004-validation-sol] |
| Registry contract owner | The `Ownable` owner of each proxy; the only address that can authorize an upgrade (`_authorizeUpgrade` is `onlyOwner`) | [src-erc-8004-identity-sol] [src-erc-8004-minimaluups-mainnet] |
| Indexers, explorers, aggregators | Read events and storage, compute off-chain reputation; not part of the spec but expected by it | [src-erc-8004-spec] [src-erc-8004-bp-reputation] |

### Reputation Registry (contract `ReputationRegistryUpgradeable`)

On-chain `Feedback` struct (storage) [src-erc-8004-reputation-sol]:

| Field | Type | Meaning |
|---|---|---|
| `value` | int128 | Signed fixed-point value; implementation bounds it to plus or minus 1e38 (`MAX_ABS_VALUE`) |
| `valueDecimals` | uint8 | 0 to 18 |
| `isRevoked` | bool | Set by `revokeFeedback` |
| `tag1` | string | Optional dimension |
| `tag2` | string | Optional sub-dimension |

Storage is keyed by `agentId`, `clientAddress` and a 1-indexed `feedbackIndex` per client per agent. `endpoint`, `feedbackURI` and `feedbackHash` are emitted in `NewFeedback` but not stored [src-erc-8004-spec] [src-erc-8004-reputation-sol].

Write functions [src-erc-8004-spec]:

| Function | Caller | Notes |
|---|---|---|
| `giveFeedback(uint256 agentId, int128 value, uint8 valueDecimals, string tag1, string tag2, string endpoint, string feedbackURI, bytes32 feedbackHash)` | any address except the owner and operators of `agentId` | Implementation reverts with "Self-feedback not allowed" via `isAuthorizedOrOwner`; reverts for a non-existent agent |
| `revokeFeedback(uint256 agentId, uint64 feedbackIndex)` | the original `clientAddress` | Sets `isRevoked`; reverts "Already revoked" |
| `appendResponse(uint256 agentId, address clientAddress, uint64 feedbackIndex, string responseURI, bytes32 responseHash)` | anyone | Implementation requires a non-empty `responseURI` and counts responses per responder |

Read functions [src-erc-8004-spec] [src-erc-8004-reputation-sol]: `getIdentityRegistry()`; `getSummary(agentId, clientAddresses[], tag1, tag2)` returns `(uint64 count, int128 summaryValue, uint8 summaryValueDecimals)` and reverts with "clientAddresses required" if the list is empty; `readFeedback(agentId, clientAddress, feedbackIndex)` returns `(value, valueDecimals, tag1, tag2, isRevoked)`; `readAllFeedback(agentId, clientAddresses[], tag1, tag2, includeRevoked)` returns parallel arrays `clients`, `feedbackIndexes`, `values`, `valueDecimals`, `tag1s`, `tag2s`, `revokedStatuses` (empty `clientAddresses` means all clients); `getResponseCount(agentId, clientAddress, feedbackIndex, responders[])`; `getClients(agentId)`; `getLastIndex(agentId, clientAddress)`.

How `getSummary` aggregates in the reference implementation [src-erc-8004-reputation-sol]: it skips revoked entries, filters by tags when non-empty, normalizes every value to 18 decimals, averages, and returns the result at the most frequent `valueDecimals` among the matched entries. It is a plain mean with no weighting.

## Message flows

All calls below are Ethereum transactions or `eth_call` reads against the registry proxies. Nothing in ERC-8004 moves value: there is no payable function and no token transfer in the three registries [src-erc-8004-identity-sol] [src-erc-8004-reputation-sol] [src-erc-8004-validation-sol]. Payments are "orthogonal to this protocol" [src-erc-8004-spec].

### Flow 1: register an agent and publish its registration file (happy path)

1. Owner prepares the registration file (fields under Core objects) and hosts it on IPFS or HTTPS, or encodes it as a base64 `data:` URI [src-erc-8004-spec].
2. Owner calls `register(agentURI)` (or `register(agentURI, metadata)`, or `register()` and later `setAgentURI`) on the Identity Registry [src-erc-8004-spec].
3. The registry mints the ERC-721 token to `msg.sender`, sets `agentWallet` to `msg.sender`, and emits `Transfer`, `Registered(agentId, agentURI, owner)` and `MetadataSet` for `agentWallet` (plus one `MetadataSet` per extra entry) [src-erc-8004-spec] [src-erc-8004-identity-sol].
4. Owner reads the new `agentId` from the `Registered` event and, if the file was written before the id was known, updates `registrations[]` in the file and calls `setAgentURI(agentId, newURI)`, which emits `URIUpdated` [src-erc-8004-spec] [src-erc-8004-contracts-readme].
5. Optional: for each HTTPS service domain that differs from the `agentURI` domain, publish `/.well-known/agent-registration.json` with a matching `registrations` entry [src-erc-8004-spec].

Failures: `register(agentURI, metadata)` reverts with "reserved key" if any entry uses `agentWallet`; `setAgentURI` and `setMetadata` revert with "Not authorized" for callers that are not owner or operator [src-erc-8004-identity-sol]. An unreachable or malformed file does not fail on-chain: the registry never reads the file, so explorers and clients must handle it.

### Flow 2: bind a payment wallet (`setAgentWallet`)

1. Owner chooses `newWallet` and a `deadline` no more than 5 minutes ahead [src-erc-8004-identity-sol].
2. `newWallet` signs the EIP-712 typed data `AgentWalletSet(agentId, newWallet, owner, deadline)` under domain `ERC8004IdentityRegistry` version `1`; a contract wallet answers ERC-1271 `isValidSignature` instead [src-erc-8004-identity-sol] [src-erc-8004-spec].
3. Owner or operator calls `setAgentWallet(agentId, newWallet, deadline, signature)`; on success the registry stores the address and emits `MetadataSet(agentId, "agentWallet", ...)` [src-erc-8004-identity-sol].

Failures (revert strings): "bad wallet" for the zero address, "expired" if past the deadline, "deadline too far" if more than 5 minutes ahead, "invalid wallet sig" if neither ECDSA nor ERC-1271 validates [src-erc-8004-identity-sol]. On any ERC-721 transfer the wallet is cleared and the new owner must repeat this flow [src-erc-8004-spec].

### Flow 3: give feedback after an x402 payment (proof of payment off-chain)

1. Client pays the agent through x402 or any other rail; ERC-8004 is not involved in the payment [src-erc-8004-spec].
2. Client writes the off-chain feedback file with the MUST fields and, optionally, `proofOfPayment { fromAddress, toAddress, chainId, txHash }`, and uploads it (IPFS suggested) [src-erc-8004-spec].
3. Client computes `feedbackHash = keccak256(file content)` (optional for IPFS) [src-erc-8004-spec].
4. Client calls `giveFeedback(agentId, value, valueDecimals, tag1, tag2, endpoint, feedbackURI, feedbackHash)` [src-erc-8004-spec].
5. The registry stores only `value`, `valueDecimals`, `tag1`, `tag2` and `isRevoked` under a new 1-indexed `feedbackIndex`, adds the client to `getClients`, and emits `NewFeedback` carrying `endpoint`, `feedbackURI` and `feedbackHash` [src-erc-8004-spec] [src-erc-8004-reputation-sol].

The registry does not verify `proofOfPayment`, the hash or the file; any verifier must fetch the file, check the hash and look the transaction up on the named chain itself [src-erc-8004-spec]. Failures: "Self-feedback not allowed" when the caller is the owner or an operator; ERC-721 `ERC721NonexistentToken` for an unknown `agentId`; "too many decimals" for `valueDecimals` above 18; "value too large" beyond plus or minus 1e38 [src-erc-8004-reputation-sol].

### Flow 4: revoke feedback and append responses

1. The original client calls `revokeFeedback(agentId, feedbackIndex)`; emits `FeedbackRevoked`. Reverts: "index must be > 0", "index out of bounds", "Already revoked" [src-erc-8004-reputation-sol].
2. Anyone calls `appendResponse(agentId, clientAddress, feedbackIndex, responseURI, responseHash)`; emits `ResponseAppended`. Reverts: "index must be > 0", "Empty URI", "index out of bounds" [src-erc-8004-reputation-sol]. Responses are counted but do not change the stored value or `getSummary` [src-erc-8004-reputation-sol].

### Flow 5: read reputation

1. Reader decides which reviewers it trusts (a list of `clientAddresses`) [src-erc-8004-spec].
2. Reader calls `getSummary(agentId, clientAddresses, tag1, tag2)` for an on-chain mean, or `readAllFeedback` plus `NewFeedback` events and off-chain files for its own scoring [src-erc-8004-spec].

Failure: an empty `clientAddresses` list reverts with "clientAddresses required"; the spec says unfiltered results "are subject to Sybil/spam attacks" [src-erc-8004-spec] [src-erc-8004-reputation-sol].

### Flow 6: validation (specified, not officially deployed)

1. Owner or operator stores the inputs and outputs to be checked at `requestURI` and calls `validationRequest(validatorAddress, agentId, requestURI, requestHash)`; emits `ValidationRequest` [src-erc-8004-spec].
2. The named validator re-executes, checks a zkML proof or a TEE attestation (the method is outside the spec) and calls `validationResponse(requestHash, response, responseURI, responseHash, tag)` with `response` from 0 to 100; emits `ValidationResponse` [src-erc-8004-spec].
3. The validator may call again for the same `requestHash`, for example soft then hard finality via `tag` [src-erc-8004-spec].

Failures in the implementation: "bad validator", "exists" (the `requestHash` was used before), "Not authorized", "unknown", "not validator", "resp>100" [src-erc-8004-validation-sol]. Incentives and slashing are out of scope [src-erc-8004-spec].

## State machines

### Agent identity lifecycle (Identity Registry)

| State | Entered by | Observable as |
|---|---|---|
| Registered without URI | `register()` | `Registered` with empty `agentURI` [src-erc-8004-identity-sol] |
| Registered with URI | `register(agentURI...)` or `setAgentURI` | `Registered` or `URIUpdated` [src-erc-8004-spec] |
| Wallet defaulted to owner | any `register` | `MetadataSet` for `agentWallet` with the owner address [src-erc-8004-identity-sol] |
| Wallet verified | `setAgentWallet` | `MetadataSet` with the new address [src-erc-8004-identity-sol] |
| Wallet cleared | `unsetAgentWallet` or any transfer | `MetadataSet` with empty value [src-erc-8004-identity-sol] |
| Transferred | ERC-721 transfer | `Transfer`; wallet cleared [src-erc-8004-spec] |
| Declared inactive | owner sets `active: false` in the off-chain file | only visible by reading the file [src-erc-8004-spec] [src-erc-8004-bp-registration] |

There is no on-chain deregistration, burn or "inactive" state in the implementation: `IdentityRegistryUpgradeable` exposes no burn function [src-erc-8004-identity-sol]. Owners can only point the URI elsewhere, set `active: false`, or transfer the token.

### Feedback entry

`given` (stored, `isRevoked = false`) to `revoked` (`isRevoked = true`) by the original client only; no un-revoke. Responses may be appended in either state and do not change it [src-erc-8004-reputation-sol].

### Validation request (specified)

`requested` (`hasResponse = false`, `response = 0`) to `responded` (`hasResponse = true`). Further responses overwrite `response`, `responseHash`, `tag` and `lastUpdate`; in the current code the value may go up or down (issue 28 reports this as a rogue-validator risk; PR 51 proposing a monotonic rule is open and unmerged as of 2026-10-11) [src-erc-8004-validation-sol] [src-erc-8004-issue-28] [src-erc-8004-pr-51].

## ERC-3643 and ONCHAINID comparison

Context. ERC-3643 ("T-REX - Token for Regulated EXchanges") is Final, Standards Track, created 2021-07-09, authors Joachim Lebrun, Tony Malghem, Kevin Thizy, Luc Falempin, Adam Boudjemaa, requires EIP-20 and EIP-173 [src-erc-3643-spec]. Its reference implementation now lives at `github.com/ERC-3643/ERC-3643`, a GitHub fork of `TokenySolutions/T-REX`, GPL-3.0, last pushed 2026-08-28 [src-erc-3643-repo]. `TokenySolutions/T-REX` is archived; its last push was 2025-10-28, and the GitHub API does not expose the exact date the archive flag was set [src-trex-repo]. Tags: the ERC-3643 organization repository has only two tags, `4.1.3` (release published 2025-06-12, marked latest) and `4.2.0-beta1` (pre-release, 2025-06-12) [src-erc-3643-repo]. The archived T-REX repository has later releases: `4.1.6` stable published 2024-10-18 (which settles the year left open in the follow-up), then pre-releases `4.2.0-beta2` (2025-01-16) and `4.1.7-beta1` (2025-02-05) [src-trex-repo]. The highest stable version number is therefore 4.1.6 in T-REX, while the current organization repository marks 4.1.3 as latest.

ERC-734 and ERC-735 were never merged as EIP files. They exist as `ethereum/EIPs` GitHub issues 734 ("ERC: Key Manager", created 2017-10-02 in its header, status WIP) and 735 ("ERC: Claim Holder", created 2017-10-09, status "Discussion"), both by Fabian Vogelsteller and both closed; the 734 text points to LSP6 Key Manager, and both carry a note that they are not fully compatible with ERC725v2 [src-eip-issue-734] [src-eip-issue-735]. `https://eips.ethereum.org/EIPS/eip-734` returned HTTP 404 on 2026-10-11. ERC-725 is Draft [src-eip-725].

ONCHAINID (`onchain-id/solidity`, GPL-3.0, `contracts/Identity.sol` last changed 2026-08-12): key purposes 1 MANAGEMENT, 2 ACTION, 3 CLAIM signer, 4 ENCRYPTION; key types 1 ECDSA, 2 RSA; `addKey` only by purpose-1 keys or the identity itself; `addClaim(topic, scheme, issuer, signature, data, uri)` only by purpose-3 keys, and a third-party issuer's claim is checked with `IClaimIssuer.isClaimValid`; claim id is `keccak256(abi.encode(issuer, topic))`; the issuer signs `keccak256(abi.encode(identity, topic, data))` with the Ethereum signed-message prefix; an `initialize(initialManagementKey)` entry point supports proxy use [src-onchainid-identity] [src-onchainid-structs]. `Claim` struct: `topic` uint256, `scheme` uint256, `issuer` address, `signature` bytes, `data` bytes, `uri` string [src-onchainid-structs].

T-REX registries from the ERC-3643 text: an Identity Registry (`registerIdentity(address _userAddress, IIdentity _identity, uint16 _country)`, `isVerified(address _userAddress)`), a Trusted Issuers Registry (`addTrustedIssuer(IClaimIssuer _trustedIssuer, uint[] _claimTopics)`), a Claim Topics Registry (`addClaimTopic(uint256 _claimTopic)`), and a Compliance contract with `canTransfer(_from, _to, _amount)` and `transferred(...)` consulted on transfers [src-erc-3643-spec].

If you come from T-REX: the word "agent" means different things. In ERC-3643 an Agent is an operator role appointed by the token owner (ERC-173) to register identities, mint, burn and freeze [src-erc-3643-spec]; in ERC-8004 an agent is the AI service itself. A `ClaimIssuer` you trust plays the role of the trusted reviewer list you pass to `getSummary`; claim topics map loosely to feedback tags; and the ERC-8004 "Identity Registry" shares a name with the T-REX Identity Registry but is a different thing (an ERC-721 agent directory, not a wallet-to-identity allowlist) [src-erc-3643-spec] [src-erc-8004-spec].

Bridge standard: ERC-8226 "Regulated Agent Mandate" (RAMS), Draft, created 2026-04-12, authors Ludovico Rossi, Dario Lo Buglio, Thamer Dridi, Nabil El Alami Khalifi (all brickken.com addresses), requires EIP-165, EIP-712, EIP-1271. It lets a verified principal delegate "scoped, time-bounded, and financially capped authority" to an agent, defines `IComplianceProvider` and `IAgentMandate`, and assigns token compliance to ERC-7943 or ERC-3643, mandate compliance to itself, and agent identity to a registry such as ERC-8004 [src-erc-8226]. No ERC3643 Association or Tokeny statement on AI agents or ERC-8004 was found in the pages searched (absence of evidence only) [src-erc3643-association].

## Relations to the other seven protocols

**x402.** The closest relation, but no protocol dependency in either direction. ERC-8004 says payments are orthogonal and shows how x402 payments "can enrich feedback signals"; its registration file carries an `x402Support` boolean; the reserved `agentWallet` key is "the address where the agent receives payments"; and the off-chain feedback file has a `proofOfPayment` object (`fromAddress`, `toAddress`, `chainId`, `txHash`) that "can be used for x402 proof of payment" [src-erc-8004-spec]. The best-practices guide suggests facilitators publish `revenues` feedback because indexers cannot easily tell x402 payments from generic transfers [src-erc-8004-bp-reputation]. The x402 specification text in the vendor clone does not mention ERC-8004 [src-x402-tsc]. People link the two: Erik Reppel co-authors ERC-8004 and represents Coinbase on the x402 Technical Steering Committee [src-erc-8004-spec] [src-x402-tsc]. The EIP editor's note in ERC-8004 asks whether the x402 reference is necessary [src-erc-8004-spec]. An open issue proposes grounding feedback in x402 payment proofs as a Sybil defense [src-erc-8004-issue-99].

**Visa Trusted Agent Protocol.** No documented relation. TAP identifies agents with RFC 9421 HTTP signatures and a Visa key directory; ERC-8004 identifies agents with an ERC-721 token on public chains. No Visa or ERC-8004 source links them; the cloned `visa-trusted-agent-protocol` repository has no mention of 8004 (searched 2026-10-11) [src-visa-tap-repo].

**OpenAI Agentic Commerce Protocol (ACP).** No documented relation found in the ACP repository or ERC-8004 sources [src-acp-repo]. Note the name clash: ERC-8183 is titled "Agentic Commerce" and calls itself the "Agentic Commerce Protocol", unrelated to OpenAI's ACP; ERC-8183 recommends integrating ERC-8004 reputation and validation [src-erc-8183].

**Google Universal Commerce Protocol (UCP).** No documented relation in the UCP repositories (no mention of 8004 in the cloned UCP repos as of 2026-10-11) [src-ucp-repo].

**Stripe and Tempo Machine Payments Protocol (MPP).** The MPP payment discovery draft (`draft-payment-discovery-01` in tempoxyz/mpp-specs) cites ERC-8004 as defining "on-chain identity registries and domain verification" and says the discovery spec operates off-chain but "is compatible with future on-chain anchoring" [src-mpp-discovery-draft]. No integration is specified.

**Google Agent Payments Protocol (AP2).** No direct mechanism in either spec. Indirect links: ERC-8004 lists A2A agent cards as `services` and reuses A2A task and skill identifiers in the feedback file, and the AP2 glossary says AP2 "can be implemented as an extension of A2A" [src-erc-8004-spec] [src-ap2-glossary]. Jordan Ellis of Google co-authors ERC-8004 [src-erc-8004-spec]. Secondary explainers describe putting an ERC-8004 id in an A2A agent card; that is a pattern, not part of AP2 (reported only). ERC-8226 is the closest on-chain analogue of an AP2 mandate and names ERC-8004 as the identity layer [src-erc-8226].

**Mastercard Agent Pay.** No documented relation. Agent Pay registers agents with Mastercard and uses agentic tokens on card rails; ERC-8004 is a public on-chain directory. No source links them; the cloned Mastercard agent toolkit and Verifiable Intent repositories have no mention of 8004 (searched 2026-10-11) [src-mastercard-toolkit-repo].

Other relations worth showing: A2A and MCP are `services` entries [src-erc-8004-spec]; ERC-8122, ERC-8217, ERC-8126 and ERC-8226 build on or around ERC-8004 (see Ecosystem); L402 is unrelated in the specs.

## Criticisms and open questions

| Criticism or question | Evidence | Source |
|---|---|---|
| Reputation is Sybil-prone by design | The spec admits it; the empirical study measures majority Sybil reviewers on all three chains studied | [src-erc-8004-spec] [src-pub-2606-26028] |
| Most registrations are placeholders | 3% to 15% live (study, to 2026-05-13); 13,210 of 505,635 ids declare an http(s) MCP, A2A or web endpoint (census, 2026-09-26) | [src-pub-2606-26028] [src-csoai-census] |
| Values are not comparable | `value` meaning depends on free-form tags; `getSummary` averages whatever matches; the study calls values "not commensurable" | [src-erc-8004-reputation-sol] [src-pub-2606-26028] |
| Feedback is not tied to real interactions | Since `feedbackAuth` was removed, any address can rate any agent; `proofOfPayment` is optional and never checked on-chain | [src-erc-8004-commit-jan07] [src-erc-8004-spec] |
| Central upgrade key | One EOA owns all three proxies on Ethereum and Base; the holder is not publicly identified | [src-erc-8004-onchain-probe] |
| Validation is unfinished | The README says the Validation Registry is under discussion with the TEE community; issue 28 (rogue validator) is open | [src-erc-8004-contracts-readme] [src-erc-8004-issue-28] |
| Non-deterministic agents | LLM outputs vary, which weakens re-execution validation; papers on reputation for LLM agents question grounding | [src-pub-2605-30169] |
| Draft status versus production use | The standard is Draft while registries run on 25 mainnets and a companion ERC that requires it is Final | [src-erc-8004-eip-page] [src-erc-8126] |
| Mutable files | HTTPS registration files can change silently | [src-erc-8004-spec] |
| Agent 0 and "incremental" ids | The spec says ids are assigned incrementally; the deployed code starts at 0, which differs from a 1-indexed reading of earlier commits | [src-erc-8004-identity-sol] [src-erc-8004-contracts-history] |
| Editorial gaps | EIP editor notes question the URIStorage dependency, the x402 example and the missing test cases | [src-erc-8004-spec] |

Open questions: Will the Validation Registry be redesigned before any listed deployment? Who controls `0x547289319C3e6aedB179C0b8e8aF0B5ACd062603`, and will ownership move to a multisig or governance (the upgrade notes recommend considering it [src-erc-8004-upgradeable-doc])? Will a JSON Schema for the registration file be published? Will the spec return to Review?

## Conflicts

1. Contracts license: Solidity files are `SPDX-License-Identifier: MIT` (CC0 for `SingletonFactory.sol`), the README "License" section says "CC0 - Public Domain", and GitHub reports no license file [src-erc-8004-identity-sol] [src-erc-8004-contracts-readme]. Use "MIT per file headers; README says CC0".
2. `tradingYield` example: the spec gives `value` `-32` with `valueDecimals` `1` for -3.2%; the best-practices copy "copied from the spec" gives `32` [src-erc-8004-spec] [src-erc-8004-bp-reputation]. The spec wins.
3. Validation Registry "not deployed": README lists none, yet a Validation proxy with implementation 2.0.0 answers at `0x8004Cc8439f36fd5F9F049D9fF86523Df6dAAB58` on Ethereum and Base [src-erc-8004-contracts-readme] [src-erc-8004-onchain-probe]. Use "specified, not officially deployed".
4. Network count: 8004scan shows 30 networks, the official README lists 25 mainnets [src-8004scan] [src-erc-8004-contracts-readme].
5. Registration cost: QuickNode and Cobo give dollars on mainnet; gas estimate at 2026-10-11 prices gives cents. Both are dated; no contradiction once dated.
6. Agent id numbering: early contracts commits moved to 1-indexed agent ids (2025-10-11), the current code mints id 0 first, and `ownerOf(0)` resolves on Ethereum [src-erc-8004-contracts-history] [src-erc-8004-identity-sol] [src-erc-8004-onchain-probe].
7. ERC-3643 "latest" tag: 4.1.3 in the ERC-3643 organization repo, 4.1.6 in the archived T-REX repo [src-erc-3643-repo] [src-trex-repo].

## Least certain

1. Whether the registration-file fields `x402Support` and `active` are required. The spec says the file "MUST have the following structure" and shows them in the example, but there is no JSON Schema and best practices treat `active` as optional ("or unset").
2. What the contract at `0x8004Cc8439f36fd5F9F049D9fF86523Df6dAAB58` is meant for operationally. It answers like the Validation implementation on Ethereum and Base, but the maintainers have not announced it; the Atlas should not present it as a supported registry.
3. The exact on-chain deployment dates per mainnet. The table uses README commit dates, which can lag deployments; the exact date T-REX was archived is also not exposed.
