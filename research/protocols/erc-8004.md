## Actors and roles

| Actor | What it does | Spec reference |
|---|---|---|
| Agent owner | Holds the ERC-721 token for an `agentId`; can transfer it, set `agentURI`, set metadata, set or unset `agentWallet`, request validation | Identity Registry [src-erc-8004-spec] |
| Operator | An address approved by the owner through ERC-721 `approve` or `setApprovalForAll`; can do what the owner does except transfer is per ERC-721 rules; cannot give feedback to the agent | [src-erc-8004-spec] [src-erc-8004-identity-sol] |
| Agent wallet | The address in the reserved `agentWallet` key where the agent "receives payments"; defaults to the owner at registration; changing it needs a signature from the new wallet | [src-erc-8004-spec] |
| Client (`clientAddress`) | Any address that calls `giveFeedback`; when the client is itself an agent it SHOULD use its `agentWallet` | [src-erc-8004-spec] |
| Responder | Anyone who calls `appendResponse` (the spec gives the agent showing a refund and a spam-tagging aggregator as examples) | [src-erc-8004-spec] |
| Validator (`validatorAddress`) | A contract or address named in `validationRequest` that alone may call `validationResponse` for that `requestHash` | [src-erc-8004-spec] [src-erc-8004-validation-sol] |
| Registry contract owner | The `Ownable` owner of each proxy; the only address that can authorize an upgrade (`_authorizeUpgrade` is `onlyOwner`) | [src-erc-8004-identity-sol] [src-erc-8004-minimaluups-mainnet] |
| Indexers, explorers, aggregators | Read events and storage, compute off-chain reputation; not part of the spec but expected by it | [src-erc-8004-spec] [src-erc-8004-bp-reputation] |

|---|---|---|---|---|

### Identity Registry (contract `IdentityRegistryUpgradeable`, ERC-721 name `AgentIdentity`, symbol `AGENT`)

Functions [src-erc-8004-spec] [src-erc-8004-identity-sol]:

| Function | Caller | Effect |
|---|---|---|
| `register()` returns `agentId` | anyone | Mints to `msg.sender`, sets `agentWallet` to `msg.sender`, URI empty |
| `register(string agentURI)` | anyone | As above plus sets the URI |
| `register(string agentURI, MetadataEntry[] metadata)` | anyone | As above plus extra metadata; reverts with "reserved key" if any key is `agentWallet` |
| `setAgentURI(uint256 agentId, string newURI)` | owner or operator | Updates the token URI, emits `URIUpdated` |
| `getMetadata(uint256 agentId, string metadataKey)` returns `bytes` | anyone | Reads metadata |
| `setMetadata(uint256 agentId, string metadataKey, bytes metadataValue)` | owner or operator | Writes metadata except the reserved `agentWallet` key |
| `setAgentWallet(uint256 agentId, address newWallet, uint256 deadline, bytes signature)` | owner or operator | Sets `agentWallet` after verifying a signature by `newWallet` |
| `getAgentWallet(uint256 agentId)` returns `address` | anyone | Reads `agentWallet` |
| `unsetAgentWallet(uint256 agentId)` | owner or operator | Clears `agentWallet` |
| `isAuthorizedOrOwner(address spender, uint256 agentId)` | anyone (used by the Reputation Registry) | Implementation helper, not in the spec |
| `getVersion()` | anyone | Returns `2.0.0` (implementation only) |

Struct `MetadataEntry`: `metadataKey` (string), `metadataValue` (bytes) [src-erc-8004-spec].

Events [src-erc-8004-spec] [src-erc-8004-identity-sol]:

| Event | Parameters |
|---|---|
| `Registered` | `uint256 indexed agentId, string agentURI, address indexed owner` |
| `URIUpdated` | `uint256 indexed agentId, string newURI, address indexed updatedBy` |
| `MetadataSet` | `uint256 indexed agentId, string indexed indexedMetadataKey, string metadataKey, bytes metadataValue` |
| `Transfer` | standard ERC-721; one per registration |

`setAgentWallet` signature details from the implementation [src-erc-8004-identity-sol]: EIP-712 domain name `ERC8004IdentityRegistry`, version `1`; typed struct `AgentWalletSet(uint256 agentId,address newWallet,address owner,uint256 deadline)`; the deadline must not be in the past and must be at most 5 minutes ahead (`MAX_DEADLINE_DELAY = 5 minutes`); ECDSA recovery is tried first (covering EOAs and EIP-7702 delegated EOAs), then ERC-1271 `isValidSignature` with magic value `0x1626ba7e`. The spec itself only says EIP-712 for EOAs and ERC-1271 for contract wallets [src-erc-8004-spec].

### Agent registration file (resolved from `agentURI`)

Allowed URI schemes named by the spec: `ipfs://`, `https://`, and base64 `data:application/json;base64,...` for fully on-chain metadata; "any URI scheme" MAY be used [src-erc-8004-spec].

| Field | Type | Required | Meaning | File |
|---|---|---|---|---|
| `type` | string (URI) | MUST (structure) | `https://eips.ethereum.org/EIPS/eip-8004#registration-v1` | `ERCS/erc-8004.md` |
| `name` | string | MUST (structure); SHOULD for ERC-721 app compatibility | Agent name | same |
| `description` | string | as above | Natural-language description, MAY include pricing and interaction methods | same |
| `image` | string (URL) | as above | Image | same |
| `services[]` | array | number and type customizable | Endpoints. Each entry has `name`, `endpoint`, optional `version` (SHOULD, not MUST); the OASF example adds optional `skills[]` and `domains[]`. Example names: `web`, `A2A`, `MCP`, `OASF`, `ENS`, `DID`, `email` | same |
| `x402Support` | boolean | shown in the required structure | Whether the agent supports x402 payments | same |
| `active` | boolean | shown in the required structure | Whether the agent is live | same |
| `registrations[]` | array of `{agentId, agentRegistry}` | SHOULD have at least one; all fields of an entry mandatory | Binds the file to one or more on-chain identities | same |
| `supportedTrust[]` | array of strings | OPTIONAL | Example values `reputation`, `crypto-economic`, `tee-attestation`; absent or empty means discovery only, not trust | same |

All rows cite [src-erc-8004-spec]. The spec says the file "MUST have the following structure" and then gives an example; it does not publish a JSON Schema, so which fields are strictly required beyond `registrations` entry fields is a reading of the example (see Least certain).

Endpoint domain verification (optional): `https://{endpoint-domain}/.well-known/agent-registration.json` containing at least a `registrations` list (or the whole file). Users MAY treat the domain as verified if a `registrations` entry matches `agentRegistry` and `agentId`; not needed when the domain already serves the file referenced by `agentURI` [src-erc-8004-spec].

### Reputation Registry (contract `ReputationRegistryUpgradeable`)

On-chain `Feedback` struct (storage) [src-erc-8004-reputation-sol]:

| Field | Type | Meaning |
|---|---|---|
| `value` | int128 | Signed fixed-point value; implementation bounds it to plus or minus 1e38 (`MAX_ABS_VALUE`) |
| `valueDecimals` | uint8 | 0 to 18 |
| `isRevoked` | bool | Set by `revokeFeedback` |
| `tag1` | string | Optional dimension |
| `tag2` | string | Optional sub-dimension |

Storage is keyed by `agentId`, `clientAddress` and a 1-indexed `feedbackIndex` per client per agent. `endpoint`, `feedbackURI` and `feedbackHash` are emitted in `NewFeedback` but not stored [src-erc-8004-spec] [src-erc-8004-reputation-sol].

Write functions [src-erc-8004-spec]:

| Function | Caller | Notes |
|---|---|---|
| `giveFeedback(uint256 agentId, int128 value, uint8 valueDecimals, string tag1, string tag2, string endpoint, string feedbackURI, bytes32 feedbackHash)` | any address except the owner and operators of `agentId` | Implementation reverts with "Self-feedback not allowed" via `isAuthorizedOrOwner`; reverts for a non-existent agent |
| `revokeFeedback(uint256 agentId, uint64 feedbackIndex)` | the original `clientAddress` | Sets `isRevoked`; reverts "Already revoked" |
| `appendResponse(uint256 agentId, address clientAddress, uint64 feedbackIndex, string responseURI, bytes32 responseHash)` | anyone | Implementation requires a non-empty `responseURI` and counts responses per responder |

Read functions [src-erc-8004-spec] [src-erc-8004-reputation-sol]: `getIdentityRegistry()`; `getSummary(agentId, clientAddresses[], tag1, tag2)` returns `(uint64 count, int128 summaryValue, uint8 summaryValueDecimals)` and reverts with "clientAddresses required" if the list is empty; `readFeedback(agentId, clientAddress, feedbackIndex)` returns `(value, valueDecimals, tag1, tag2, isRevoked)`; `readAllFeedback(agentId, clientAddresses[], tag1, tag2, includeRevoked)` returns parallel arrays `clients`, `feedbackIndexes`, `values`, `valueDecimals`, `tag1s`, `tag2s`, `revokedStatuses` (empty `clientAddresses` means all clients); `getResponseCount(agentId, clientAddress, feedbackIndex, responders[])`; `getClients(agentId)`; `getLastIndex(agentId, clientAddress)`.

How `getSummary` aggregates in the reference implementation [src-erc-8004-reputation-sol]: it skips revoked entries, filters by tags when non-empty, normalizes every value to 18 decimals, averages, and returns the result at the most frequent `valueDecimals` among the matched entries. It is a plain mean with no weighting.

Events [src-erc-8004-spec]:

| Event | Parameters |
|---|---|
| `NewFeedback` | `uint256 indexed agentId, address indexed clientAddress, uint64 feedbackIndex, int128 value, uint8 valueDecimals, string indexed indexedTag1, string tag1, string tag2, string endpoint, string feedbackURI, bytes32 feedbackHash` |
| `FeedbackRevoked` | `uint256 indexed agentId, address indexed clientAddress, uint64 indexed feedbackIndex` |
| `ResponseAppended` | `uint256 indexed agentId, address indexed clientAddress, uint64 feedbackIndex, address indexed responder, string responseURI, bytes32 responseHash` |

Example `tag1` values from the spec table: `starred`, `reachable`, `ownerVerified`, `uptime`, `successRate`, `responseTime`, `blocktimeFreshness`, `revenues`, `tradingYield` (with `tag2` of `day`, `week`, `month`, `year`) [src-erc-8004-spec].

### Validation Registry (contract `ValidationRegistryUpgradeable`, specified, not officially deployed)

| Item | Exact form | Source |
|---|---|---|
| Request | `validationRequest(address validatorAddress, uint256 agentId, string requestURI, bytes32 requestHash)`; MUST be called by owner or operator; `requestHash` is keccak256 of the request payload and identifies the request | [src-erc-8004-spec] |
| Response | `validationResponse(bytes32 requestHash, uint8 response, string responseURI, bytes32 responseHash, string tag)`; only the named validator; `response` 0 to 100; may be called many times (for example soft then hard finality via `tag`) | [src-erc-8004-spec] |
| Events | `ValidationRequest(address indexed validatorAddress, uint256 indexed agentId, string requestURI, bytes32 indexed requestHash)`; `ValidationResponse(address indexed validatorAddress, uint256 indexed agentId, bytes32 indexed requestHash, uint8 response, string responseURI, bytes32 responseHash, string tag)` | [src-erc-8004-spec] |
| Stored | `requestHash`, `validatorAddress`, `agentId`, `response`, `responseHash`, `lastUpdate`, `tag` (implementation adds `hasResponse`) | [src-erc-8004-spec] [src-erc-8004-validation-sol] |
| Reads | `getValidationStatus(requestHash)`; `getSummary(agentId, validatorAddresses[], tag)` returns `(uint64 count, uint8 averageResponse)` (implementation names it `avgResponse`); `getAgentValidations(agentId)`; `getValidatorRequests(validatorAddress)` | [src-erc-8004-spec] [src-erc-8004-validation-sol] |
| Implementation guard | `validationRequest` reverts with "exists" if the `requestHash` was used before | [src-erc-8004-validation-sol] |

Deployment status: the contracts README lists no Validation Registry address on any chain and carries a warning that this part of the spec is "still under active update and discussion with the TEE community" [src-erc-8004-contracts-readme]. Testnet Validation addresses were listed from 2025-10-22 and dropped from the README on 2026-01-06 (the 2026-01-08 testnet list has none) [src-erc-8004-readme-history]. However, `scripts/addresses.ts` names a mainnet Validation proxy address `0x8004Cc8439f36fd5F9F049D9fF86523Df6dAAB58` [src-erc-8004-addresses-ts], and on 2026-10-11 a contract at that address on Ethereum and on Base answered `getVersion()` with `2.0.0`, `getIdentityRegistry()` with the Identity Registry address, and `owner()` with the same EOA as the other two proxies [src-erc-8004-onchain-probe]. So a Validation implementation sits at the scripted address on at least those two chains, but it is not listed, documented or announced as deployed. The Atlas should say "specified, not officially deployed" and must not present that address as a supported registry.
