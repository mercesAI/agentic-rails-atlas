## Actors and roles

| Actor | What it does | Spec reference |
|---|---|---|
| Agent owner | Holds the ERC-721 token for an `agentId`; can transfer it, set `agentURI`, set metadata, set or unset `agentWallet`, request validation | Identity Registry [src-erc-8004-spec] |
| Operator | An address approved by the owner through ERC-721 `approve` or `setApprovalForAll`; can do what the owner does except transfer is per ERC-721 rules; cannot give feedback to the agent | [src-erc-8004-spec] [src-erc-8004-identity-sol] |
| Agent wallet | The address in the reserved `agentWallet` key where the agent "receives payments"; defaults to the owner at registration; changing it needs a signature from the new wallet | [src-erc-8004-spec] |
| Client (`clientAddress`) | Any address that calls `giveFeedback`; when the client is itself an agent it SHOULD use its `agentWallet` | [src-erc-8004-spec] |
| Responder | Anyone who calls `appendResponse` (the spec gives the agent showing a refund and a spam-tagging aggregator as examples) | [src-erc-8004-spec] |
| Validator (`validatorAddress`) | A contract or address named in `validationRequest` that alone may call `validationResponse` for that `requestHash` | [src-erc-8004-spec] [src-erc-8004-validation-sol] |
| Registry contract owner | The `Ownable` owner of each proxy; the only address that can authorize an upgrade (`_authorizeUpgrade` is `onlyOwner`) | [src-erc-8004-identity-sol] [src-erc-8004-minimaluups-mainnet] |
| Indexers, explorers, aggregators | Read events and storage, compute off-chain reputation; not part of the spec but expected by it | [src-erc-8004-spec] [src-erc-8004-bp-reputation] |

### Reputation Registry (contract `ReputationRegistryUpgradeable`)

On-chain `Feedback` struct (storage) [src-erc-8004-reputation-sol]:

| Field | Type | Meaning |
|---|---|---|
| `value` | int128 | Signed fixed-point value; implementation bounds it to plus or minus 1e38 (`MAX_ABS_VALUE`) |
| `valueDecimals` | uint8 | 0 to 18 |
| `isRevoked` | bool | Set by `revokeFeedback` |
| `tag1` | string | Optional dimension |
| `tag2` | string | Optional sub-dimension |

Storage is keyed by `agentId`, `clientAddress` and a 1-indexed `feedbackIndex` per client per agent. `endpoint`, `feedbackURI` and `feedbackHash` are emitted in `NewFeedback` but not stored [src-erc-8004-spec] [src-erc-8004-reputation-sol].

Write functions [src-erc-8004-spec]:

| Function | Caller | Notes |
|---|---|---|
| `giveFeedback(uint256 agentId, int128 value, uint8 valueDecimals, string tag1, string tag2, string endpoint, string feedbackURI, bytes32 feedbackHash)` | any address except the owner and operators of `agentId` | Implementation reverts with "Self-feedback not allowed" via `isAuthorizedOrOwner`; reverts for a non-existent agent |
| `revokeFeedback(uint256 agentId, uint64 feedbackIndex)` | the original `clientAddress` | Sets `isRevoked`; reverts "Already revoked" |
| `appendResponse(uint256 agentId, address clientAddress, uint64 feedbackIndex, string responseURI, bytes32 responseHash)` | anyone | Implementation requires a non-empty `responseURI` and counts responses per responder |

Read functions [src-erc-8004-spec] [src-erc-8004-reputation-sol]: `getIdentityRegistry()`; `getSummary(agentId, clientAddresses[], tag1, tag2)` returns `(uint64 count, int128 summaryValue, uint8 summaryValueDecimals)` and reverts with "clientAddresses required" if the list is empty; `readFeedback(agentId, clientAddress, feedbackIndex)` returns `(value, valueDecimals, tag1, tag2, isRevoked)`; `readAllFeedback(agentId, clientAddresses[], tag1, tag2, includeRevoked)` returns parallel arrays `clients`, `feedbackIndexes`, `values`, `valueDecimals`, `tag1s`, `tag2s`, `revokedStatuses` (empty `clientAddresses` means all clients); `getResponseCount(agentId, clientAddress, feedbackIndex, responders[])`; `getClients(agentId)`; `getLastIndex(agentId, clientAddress)`.

How `getSummary` aggregates in the reference implementation [src-erc-8004-reputation-sol]: it skips revoked entries, filters by tags when non-empty, normalizes every value to 18 decimals, averages, and returns the result at the most frequent `valueDecimals` among the matched entries. It is a plain mean with no weighting.

## Message flows

All calls below are Ethereum transactions or `eth_call` reads against the registry proxies. Nothing in ERC-8004 moves value: there is no payable function and no token transfer in the three registries [src-erc-8004-identity-sol] [src-erc-8004-reputation-sol] [src-erc-8004-validation-sol]. Payments are "orthogonal to this protocol" [src-erc-8004-spec].

### Flow 1: register an agent and publish its registration file (happy path)

1. Owner prepares the registration file (fields under Core objects) and hosts it on IPFS or HTTPS, or encodes it as a base64 `data:` URI [src-erc-8004-spec].
2. Owner calls `register(agentURI)` (or `register(agentURI, metadata)`, or `register()` and later `setAgentURI`) on the Identity Registry [src-erc-8004-spec].
3. The registry mints the ERC-721 token to `msg.sender`, sets `agentWallet` to `msg.sender`, and emits `Transfer`, `Registered(agentId, agentURI, owner)` and `MetadataSet` for `agentWallet` (plus one `MetadataSet` per extra entry) [src-erc-8004-spec] [src-erc-8004-identity-sol].
4. Owner reads the new `agentId` from the `Registered` event and, if the file was written before the id was known, updates `registrations[]` in the file and calls `setAgentURI(agentId, newURI)`, which emits `URIUpdated` [src-erc-8004-spec] [src-erc-8004-contracts-readme].
5. Optional: for each HTTPS service domain that differs from the `agentURI` domain, publish `/.well-known/agent-registration.json` with a matching `registrations` entry [src-erc-8004-spec].

Failures: `register(agentURI, metadata)` reverts with "reserved key" if any entry uses `agentWallet`; `setAgentURI` and `setMetadata` revert with "Not authorized" for callers that are not owner or operator [src-erc-8004-identity-sol]. An unreachable or malformed file does not fail on-chain: the registry never reads the file, so explorers and clients must handle it.

### Flow 2: bind a payment wallet (`setAgentWallet`)

1. Owner chooses `newWallet` and a `deadline` no more than 5 minutes ahead [src-erc-8004-identity-sol].
2. `newWallet` signs the EIP-712 typed data `AgentWalletSet(agentId, newWallet, owner, deadline)` under domain `ERC8004IdentityRegistry` version `1`; a contract wallet answers ERC-1271 `isValidSignature` instead [src-erc-8004-identity-sol] [src-erc-8004-spec].
3. Owner or operator calls `setAgentWallet(agentId, newWallet, deadline, signature)`; on success the registry stores the address and emits `MetadataSet(agentId, "agentWallet", ...)` [src-erc-8004-identity-sol].

Failures (revert strings): "bad wallet" for the zero address, "expired" if past the deadline, "deadline too far" if more than 5 minutes ahead, "invalid wallet sig" if neither ECDSA nor ERC-1271 validates [src-erc-8004-identity-sol]. On any ERC-721 transfer the wallet is cleared and the new owner must repeat this flow [src-erc-8004-spec].

### Flow 3: give feedback after an x402 payment (proof of payment off-chain)

1. Client pays the agent through x402 or any other rail; ERC-8004 is not involved in the payment [src-erc-8004-spec].
2. Client writes the off-chain feedback file with the MUST fields and, optionally, `proofOfPayment { fromAddress, toAddress, chainId, txHash }`, and uploads it (IPFS suggested) [src-erc-8004-spec].
3. Client computes `feedbackHash = keccak256(file content)` (optional for IPFS) [src-erc-8004-spec].
4. Client calls `giveFeedback(agentId, value, valueDecimals, tag1, tag2, endpoint, feedbackURI, feedbackHash)` [src-erc-8004-spec].
5. The registry stores only `value`, `valueDecimals`, `tag1`, `tag2` and `isRevoked` under a new 1-indexed `feedbackIndex`, adds the client to `getClients`, and emits `NewFeedback` carrying `endpoint`, `feedbackURI` and `feedbackHash` [src-erc-8004-spec] [src-erc-8004-reputation-sol].

The registry does not verify `proofOfPayment`, the hash or the file; any verifier must fetch the file, check the hash and look the transaction up on the named chain itself [src-erc-8004-spec]. Failures: "Self-feedback not allowed" when the caller is the owner or an operator; ERC-721 `ERC721NonexistentToken` for an unknown `agentId`; "too many decimals" for `valueDecimals` above 18; "value too large" beyond plus or minus 1e38 [src-erc-8004-reputation-sol].

### Flow 4: revoke feedback and append responses

1. The original client calls `revokeFeedback(agentId, feedbackIndex)`; emits `FeedbackRevoked`. Reverts: "index must be > 0", "index out of bounds", "Already revoked" [src-erc-8004-reputation-sol].
2. Anyone calls `appendResponse(agentId, clientAddress, feedbackIndex, responseURI, responseHash)`; emits `ResponseAppended`. Reverts: "index must be > 0", "Empty URI", "index out of bounds" [src-erc-8004-reputation-sol]. Responses are counted but do not change the stored value or `getSummary` [src-erc-8004-reputation-sol].

### Flow 5: read reputation

1. Reader decides which reviewers it trusts (a list of `clientAddresses`) [src-erc-8004-spec].
2. Reader calls `getSummary(agentId, clientAddresses, tag1, tag2)` for an on-chain mean, or `readAllFeedback` plus `NewFeedback` events and off-chain files for its own scoring [src-erc-8004-spec].

Failure: an empty `clientAddresses` list reverts with "clientAddresses required"; the spec says unfiltered results "are subject to Sybil/spam attacks" [src-erc-8004-spec] [src-erc-8004-reputation-sol].

### Flow 6: validation (specified, not officially deployed)

1. Owner or operator stores the inputs and outputs to be checked at `requestURI` and calls `validationRequest(validatorAddress, agentId, requestURI, requestHash)`; emits `ValidationRequest` [src-erc-8004-spec].
2. The named validator re-executes, checks a zkML proof or a TEE attestation (the method is outside the spec) and calls `validationResponse(requestHash, response, responseURI, responseHash, tag)` with `response` from 0 to 100; emits `ValidationResponse` [src-erc-8004-spec].
3. The validator may call again for the same `requestHash`, for example soft then hard finality via `tag` [src-erc-8004-spec].

Failures in the implementation: "bad validator", "exists" (the `requestHash` was used before), "Not authorized", "unknown", "not validator", "resp>100" [src-erc-8004-validation-sol]. Incentives and slashing are out of scope [src-erc-8004-spec].

## State machines

### Agent identity lifecycle (Identity Registry)

| State | Entered by | Observable as |
|---|---|---|
| Registered without URI | `register()` | `Registered` with empty `agentURI` [src-erc-8004-identity-sol] |
| Registered with URI | `register(agentURI...)` or `setAgentURI` | `Registered` or `URIUpdated` [src-erc-8004-spec] |
| Wallet defaulted to owner | any `register` | `MetadataSet` for `agentWallet` with the owner address [src-erc-8004-identity-sol] |
| Wallet verified | `setAgentWallet` | `MetadataSet` with the new address [src-erc-8004-identity-sol] |
| Wallet cleared | `unsetAgentWallet` or any transfer | `MetadataSet` with empty value [src-erc-8004-identity-sol] |
| Transferred | ERC-721 transfer | `Transfer`; wallet cleared [src-erc-8004-spec] |
| Declared inactive | owner sets `active: false` in the off-chain file | only visible by reading the file [src-erc-8004-spec] [src-erc-8004-bp-registration] |

There is no on-chain deregistration, burn or "inactive" state in the implementation: `IdentityRegistryUpgradeable` exposes no burn function [src-erc-8004-identity-sol]. Owners can only point the URI elsewhere, set `active: false`, or transfer the token.

### Feedback entry

`given` (stored, `isRevoked = false`) to `revoked` (`isRevoked = true`) by the original client only; no un-revoke. Responses may be appended in either state and do not change it [src-erc-8004-reputation-sol].

### Validation request (specified)

`requested` (`hasResponse = false`, `response = 0`) to `responded` (`hasResponse = true`). Further responses overwrite `response`, `responseHash`, `tag` and `lastUpdate`; in the current code the value may go up or down (issue 28 reports this as a rogue-validator risk; PR 51 proposing a monotonic rule is open and unmerged as of 2026-10-11) [src-erc-8004-validation-sol] [src-erc-8004-issue-28] [src-erc-8004-pr-51].

## Security model and published attacks or CVEs

No CVE and no GitHub security advisory was found for `erc-8004/erc-8004-contracts` (the repository advisory list was empty on 2026-10-11) [src-erc-8004-contracts-history]. No audit report by a named audit firm is published in the repository. A contract commit of 2025-11-12 is titled "fix audit issue validation score 0 affecting getsummary", which shows that some review happened but not by whom [src-erc-8004-commit-audit-fix]. A community audit PR (PR 51, 2026-02-13) reports 1 high, 3 medium, 3 low and 2 informational findings and remains open and unmerged [src-erc-8004-pr-51].

| Risk | What the sources say | Source |
|---|---|---|
| Sybil feedback | The spec says Sybil attacks "are possible"; mitigation is filtering by trusted reviewers, which `getSummary` enforces by requiring a client list | [src-erc-8004-spec] |
| Measured Sybil behavior | 73.5% (Ethereum), 59.2% (BSC) and 90.6% (Base) of reviewers showed coordinated Sybil behavior in data to 2026-05-13 | [src-pub-2606-26028] |
| Self-rating | Blocked for owner and operators only; a fresh address controlled by the owner can still rate | [src-erc-8004-reputation-sol] [src-erc-8004-spec] |
| Mutable registration files | `agentURI` can be changed at any time by owner or operator; `https://` files can change without an on-chain event; only content-addressed URIs pin content | [src-erc-8004-spec] [src-erc-8004-identity-sol] |
| Capability claims | The spec says it cannot guarantee advertised capabilities are "functional and non-malicious" | [src-erc-8004-spec] |
| Upgradeability | All three proxies are UUPS with `_authorizeUpgrade` restricted to `onlyOwner`; on Ethereum and Base the owner on 2026-10-11 was `0x547289319C3e6aedB179C0b8e8aF0B5ACd062603`, which has no contract code (an externally owned account, not a multisig contract). Who holds that key is not published | [src-erc-8004-minimaluups-mainnet] [src-erc-8004-onchain-probe] [src-erc-8004-issue-95] |
| Rogue validator | A validator can lower a response after a pass (issue 28, open) | [src-erc-8004-issue-28] |
| `requestHash` first-come rule | `validationRequest` rejects a `requestHash` already used ("exists"), and the hash is a global key, so any agent owner who learns a hash first can occupy it. This is a reading of the code; no exploit report was found | [src-erc-8004-validation-sol] |
| Unbounded reads | `getSummary` and `readAllFeedback` loop over all entries per client; the community audit lists unbounded array returns and quadratic gas | [src-erc-8004-reputation-sol] [src-erc-8004-pr-51] |
| Wallet binding replay | Signatures expire within 5 minutes and include `owner`, `agentId` and the chain-bound EIP-712 domain; there is no nonce, so a signature can be reused inside its window for the same tuple | [src-erc-8004-identity-sol] |
| Non-comparable values | `value` units depend on tags; the empirical study says values "are not commensurable" | [src-pub-2606-26028] |
