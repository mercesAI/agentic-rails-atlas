# CLAUDE.md: conventions for the Agentic Rails Atlas

Read `PLAN.md` and the tail of `private/PROGRESS.md` first. The full specification is `private/ATLAS_PROMPT.md`; `private/DECISIONS.md` records every judgment call.

## What this is
A static, offline-capable Astro site that explains eight agent identity, checkout and payment protocols (ERC-8004, x402, Visa TAP, OpenAI ACP, UCP, Stripe MPP, AP2, Mastercard Agent Pay) with sourced claims, diagrams, an ASD-STE100 version, personas, resources, verified publications, security, controls, compliance, observability and playgrounds.

## Non-negotiables
- Every factual claim has a source record and a confidence (`verified`, `reported`, `unverified`). Numbers carry an `asOf` date. Never invent field names, endpoints, dates, version numbers or partner names. Read the cloned specs in `research/vendor/` for field names.
- No em dashes in site content (`pnpm lint:style` fails the build). No banned stock phrases (`scripts/style/banned-phrases.json`). US spelling. Sentence-case headings. Dates as YYYY-MM-DD.
- Original prose and diagrams. At most one quotation under 15 words per source. No logos. Spec text is linked, not copied.
- No real funds, keys, wallet connections or sign-ups. Playgrounds are simulations with ephemeral in-browser keys on fake chain IDs.
- Never write outside the project folder. Never commit `research/vendor/` or `ste/approved-words.local.txt`.

## Stack
Astro 7 (static output) + React 19 islands + TypeScript strict + MDX + Zod content collections; Tailwind CSS 4 via `@tailwindcss/vite` plus CSS custom properties in `src/styles/tokens.css`; D3 for the bubble universe; `@xyflow/react` for stack and controls maps; Mermaid rendered at build time by `scripts/render-diagrams.ts` (Playwright) to light and dark SVG; Shiki; Pagefind; `compromise` for STE heuristics; Vitest; Playwright + axe. pnpm with exact pinned versions.

## Layout
See private/ATLAS_PROMPT.md 12.2. Content lives in `src/content/`; schemas in `src/lib/schemas.ts`; flows are JSON in `src/content/flows/` and are the single source of truth for sequence diagrams and the flow player; generated artifacts land in `src/generated/` (committed, regenerated by scripts).

## Writing exemplars (from private/ATLAS_FOLLOWUP.md 3.1; match this register)

Practitioner register (x402, opening of section B):

> x402 answers one question: how does a server charge for a single HTTP request without accounts, API keys or invoices? The server replies 402 with a header that lists what it accepts: a scheme, a network, an amount, an asset and a payee address. The client signs a payment that matches one of those entries and retries the same request with the signature in a header. The server never touches a chain itself. It hands the signature to a facilitator, which checks it (verify), lets the server respond, then submits it on-chain (settle). The client's signature binds the amount and the recipient, so a facilitator cannot redirect funds, and a nonce with a validity window stops replays. What x402 does not give you: refunds under the exact scheme, a dispute process, or any statement about who the client is. Those live in other layers: the auth-capture scheme, ERC-8004, or your own policy.

STE register (x402, one procedure plus one safety instruction):

> **Pay for a resource with x402 (client)**
> 1. Send the request to the server.
> 2. If the server sends status 402, read the PAYMENT-REQUIRED header.
> 3. Decode the header. Find the payment option that your wallet supports.
> 4. Make sure that the amount and the payTo address are correct.
> 5. Sign the payment with your key.
> 6. Send the request again. Put the signed payment in the PAYMENT-SIGNATURE header.
> 7. Read the PAYMENT-RESPONSE header. Keep the transaction identifier.
>
> CAUTION: DO NOT SIGN A PAYMENT IF THE payTo ADDRESS IS NOT THE ADDRESS THAT YOU EXPECT. YOU CANNOT REVERSE AN EXACT SETTLEMENT.
